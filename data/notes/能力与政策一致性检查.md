# 能力与政策一致性检查（三层方案）

## 背景与动机

出处：来自《三级信息政策》笔记中踩坑的延续。

- **2026-09-05 踩坑**：M3 阶段写的提示词「只依据资料回答」，到了 M5 加工具后开始"打架"——模型宁可停下来问许可，也不敢主动调工具。
- **修订结果**：改为三级信息政策「资料优先 → 工具补充 → 都没有时用通用知识并标注来源」。
- **延伸出的核心问题**：给 agent 每加一个新能力（工具、数据源、技能模块），旧的约束政策可能就不再成立。项目变大、能力变多后，**人工逐步复查政策是否仍成立**变得越来越不可行、迟早遗漏。

> 主线教训：**能力是变量，政策是约束。新增能力 = 可能需要修订旧政策的信号。** 复查不能只靠记性和自觉，需要一个可持续、可自动化的检查体系，这就是本文的三层方案。

## 三层方案设计

按"成本从低到高、广度从小到大"叠成三层，越上层越贵、只对关键场景启用。

### 第 1 层：变更驱动的触发式复查（人在环上，成本最低）

只要**任何能力被新增/修改**（加一个工具、改一个数据源、加一个技能模块），就自动挂起一个「一致性复查任务」，强制人工逐条过一遍受影响政策。

- **触发点**：能力清单（tools / skills / data_sources）的 diff 检测到变化。
- **复查粒度**：只复查「与该能力相关的旧政策」，不必全量扫描。
- **产出**：一张"本能力 ↔ 关联政策是否仍成立"检查表，勾完才算变更完成。
- **落点**：把它做成 commit / PR / 发布 gates——不通过就不允许合入或上线。

### 第 2 层：规则化的静态一致性扫描（自动化判子，中成本）

把"政策与能力的适配关系"写成**可机读的规则/断言**，每次 CI 运行扫描，自动报出明显冲突。

- 例如旧政策写着「禁止调用任何工具」= 白名单为空；新增工具后若未更新该政策，断言就会失败并定位到冲突行。
- **优势**：无需人逐条看，能抓到"忘了复查"的遗漏，覆盖所有历史变更。
- **局限**：只能捕获可形式化的冲突（能不能调、白黑名单、顺序、是否允许外带信息等），抓不到语义层的软冲突——需要第 3 层。

### 第 3 层：评测集驱动的语义回归测试（验证行为，成本最高）

真实跑场景，用**行为结果**验证"政策本意"在新能力下是否被守住。

- 构造回归测试集：把每一条重要政策都搭 2~3 个能暴露其本意的场景用例（含正例 + 反例/边界）。
- 例：针对「资料优先」政策，造一个"资料里答不了、但工具能拿到答案"的用例，看模型是死板问许可、还是按三级政策去调工具。
- **判定**：不是看一句输出，而是看**信息路径**是否符合政策（走了工具？走了资料？是否标注了来源？）。
- **落点**：做成自动化跑分 / golden set，作为每个里程碑的"政策健康报告"。

## 三层如何配合

| 层 | 触发方式 | 成本 | 覆盖 | 主要价值 |
|---|---|---|---|---|
| 1 变更触发复查 | 能力 diff 触发 | 低 | 当前变更 | 不放过任何新改动 |
| 2 静态一致性扫描 | CI 全量跑 | 中 | 历史全部变更 | 自动抓"忘了复查"的遗漏 |
| 3 语义回归测试 | milestone 跑 | 高 | 政策本意 | 验证行为符合政策，抓语义软冲突 |

- 第 1 层保证"每次改动都过问"；
- 第 2 层保证"过去的改动没漏"；
- 第 3 层保证"文字写得对、真跑起来也对"。

## 一句话总结

给 agent 加能力时，**永远先问一句"这会动摇哪条旧政策？"**，并把这种复查从"靠人记得"升级为"变更→规则→行为"三层的自动化/半自动化校验，让项目再大也不翻车。
