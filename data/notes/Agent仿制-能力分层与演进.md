# Agent 仿制：复杂任务能力的分层拆解与演进方法论

> 场景：以"做项目 + 仿制 coding agent（类 Qoder）"的方式学 AI Agent 开发。
> 核心矛盾：**想要的东西是"能可靠完成复杂任务"，而不是"demo 能跑通"。**

## 一、先定位：三条学习路径 ≠ 同一维度，不可强行拉齐

| 路径 | 代表 | 目标维度 | 交付物 |
|---|---|---|---|
| demo 类项目 | 能跑的最小示例 | 宽度 | 跑通即可 |
| 企业级课程 | 上线要过的关 | 深度 | 能上线 |
| 前沿论文 | 下一轮升级方向 | 高度 | 前瞻 |

- 三条路径分别对应**宽度 / 深度 / 高度**，性质不同，别指望一份材料同时满足三者。
- 正确姿势：**以项目为主线，让课程和论文为项目服务**——
  - 课程逼项目做"生产化改造"（补日志、重试、超时、成本、安全）；
  - 论文给项目选"下一个升级课题"（鲁棒 tool-use、自纠错、记忆分层）。
- 每轮固定输出物沉淀收获（例如"设计取舍说明"），避免做完了说不清为什么这么设计。

## 二、目标能力的四层拆解（想仿制什么，先拆清它由哪几层组成）

1. **底层 LLM** —— 直接调 API，不需要自己训练。真正的难点不在这一层，在下层。
2. **Agent 骨架** —— 规划 + 工具调用的循环；这是复刻的第一块最小可跑样板。
3. **工具能力与约束政策** —— 关键点在此：**新增一个工具/能力，往往会动摇已有的旧政策**（详见下文第三部分，交叉引用：`能力与政策一致性检查.md`）。
4. **使人信任的工程** —— 需追踪"实际调用序列"，防止"嘴上说做了其实没调工具"装乖不干活（交叉引用：`政策自动复查落地手册.md`、`一致性检查-第2_3层实操示例.md`）。

## 三、实操节奏：先复刻最小骨架，再按"是否动摇旧政策"演进

1. 第一步只做**最小"规划 + 工具循环"**，让它先能跑。
2. 之后每加一个能力，先问：**这会动摇我已有的哪条旧政策/旧假设？**
   - 主线教训：**能力是变量，政策是约束。新增能力 = 可能需要修订旧政策的信号。**
3. 用"被测 agent = 自己正在做的仿制品"，反向积累真实测试用例（某条政策在加了新能力后破了，就是一条好用例）。
