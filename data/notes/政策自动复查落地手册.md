# 政策自动复查 · 落地手册

> 出处整理：配套 [[能力与政策一致性检查]]、[[一致性检查-第2_3层实操示例]]。
> 回答「政策复查怎么自动化」——核心思路是把政策从自然语言改写为**可机读数据 + 规则 + 可观测行为路径**，交给 CI/评测集去比对，摆脱"靠人记"。

## 核心思想

能力是变量 = 新增/修改能力时需要修订旧政策的信号。
自动化复查 = 让"能力数据、静态断言、行为路径"三者自动比对，替代人工逐一过检查单。

## 三层总览

| 层 | 触发方式 | 成本 | 覆盖 | 主要价值 |
|---|---|---|---|---|
| 1 变更触发复查 | 能力 diff 触发，人在环上 | 低 | 当前变更 | 每次改动都过问 |
| 2 静态一致性扫描 | CI 全量跑 | 中 | 历史全部变更 | 自动抓"忘了复查"遗漏 |
| 3 语义回归测试 | milestone 跑 | 高 | 政策本意 | 用信息路径验证行为，抓软冲突 |

落地顺序：先 1 止血 → 加 2 兜底 → 攒 3 验语义。

## 第 1 层：变更驱动触发式复查

- 触发点：能力清单（tools / skills / data_sources）的 diff 检测到变化。
- 动作：自动挂起「一致性复查任务」，强制人工逐条过受影响政策。
- 产出：一张"本能力 ↔ 关联政策是否仍成立"检查表。
- 落点：做成 commit / PR / 发布 gates，不通过不允许合入/上线。

## 第 2 层：规则化静态一致性扫描（自动化判子的核心）

把政策翻译成三份可机读数据，CI 全量对跑。

### A. 能力清单（单一事实来源）
每个能力带 `kind`（行为大类）+ `external_io`（是否把数据送出本域）——这是后期能"硬判"的最小抓手。

```jsonc
{
  "tools": [
    { "name": "web_search", "kind": "network",  "external_io": true  },
    { "name": "read_note",   "kind": "local_kb", "external_io": false },
    { "name": "run_shell",   "kind": "shell",    "external_io": true  }
  ]
}
```

### B. 政策 → 规则（自然语言变条件）
以踩坑旧句式"只依据资料回答"为例 → 规则：

- **TOOL-ALLOWLIST_SYNC**：凡在政策中声明了 tool 约束的，可用工具白名单必须 ⊇ capabilities 中声明的该角色数据集。（反例：旧政策隐含白名单为空，后来悄悄加了 web_search，白名单没跟着涨 → 断言失败定位到冲突。）
- **IO-BOUNDARY**：`external_io=true` 的能力不得出现在标注为 local-only 的 policy scope 内。

### C. 落进 CI
用 JSON-schema 校验 capabilities.json + 脚本遍历 policy scope 与能力白名单做**子集校验**。任一 diff 未同步即红掉，CI 失败拦住合入。

### D. 通用警觉
规则颗粒度别太细，先抓两类最常翻车的硬冲突即可：
1. **能不能调用**：政策声明白名单 与 实际注册工具集合 是否子集一致；
2. **数据能不能出去**：external_io=true 工具是否放进"仅内部"作用域。

其余语义软冲突全部下沉第 3 层。

## 第 3 层：评测集驱动的语义回归测试

不是看一句话，而是观测 agent 的**信息路径（调用序列）**是否守住政策本意。

### A. 用例骨架（每条政策 3 例：正例/反例/边界）
```jsonc
{
  "policy_id": "三级信息政策·资料优先",
  "intent": "资料能答→用资料；资料答不了但工具有→调工具；都没有→通用知识并标注",
  "cases": [
    { "role": "positive", "scenario": "资料含答案，工具也开着", "expect_path": ["read资料"] },
    { "role": "negative", "scenario": "资料没答案但 web_search 能取到", "expect_path": ["调用tool"], "note": "踩坑复现" },
    { "role": "boundary", "scenario": "资料工具都没有答案", "expect_path": ["通用知识"], "expect_flag": "must标注来源" }
  ]
}
```

### B. 判定方式：记录信息路径，别只看最终文本
给被测 agent 挂**调用追踪探针**，记录实际走了 read / tool / 直接答 哪条路，再与 expect_path 比对。
- 只看文字易误判（可能嘴上说"查一下"其实没调工具）；
- 看调用序列 + 是否 ask_permission，能击穿"装乖不干活 / 不敢动"的假通过。

### C. 用例设计提醒
- 正/反/边界都要造，只造正例会自我感觉良好。
- 故意放一个"踩坑复现"用例（如 M3"只依据资料"× M5 加工具），做成一劳永逸的回归锚点。
- 跑分产物收敛成 **golden set**，作为每里程碑政策健康基线，可对比折线。

## 一句话总结

加能力时永远先问"这会动摇哪条旧政策？"，并把复查升级为「变更 → 规则 → 行为」三层的自动化/半自动化校验，让项目再大也不翻车。—— 政策复查自动化 = 靠机读数据、静态断言、调用路径的自动比对，而非人的记性。
