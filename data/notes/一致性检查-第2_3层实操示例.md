# 一致性检查 · 第 2、3 层实操示例

> 姊妹笔记，配套 [[能力与政策一致性检查]] 使用——那篇讲"三层方案是什么"，这篇给"第 2 层规则怎么写、第 3 层评测集怎么造"的可执行细节。

## 第 2 层：规则化静态扫描的落地写法

核心是把政策翻译成**可机读的能力清单 + 能力类白名单 + 断言规则**三份数据，CI 全量对跑。

### A. 能力清单（单一事实来源）

把 agent 声明的所有能力统一登记，每个能力都带一个 `kind` 便于归类审查：

```jsonc
// capabilities.json  （tools / skills / data_sources 各自一份，这里以 tools 为例）
{
  "tools": [
    { "name": "web_search",           "kind": "network",      "external_io": true },
    { "name": "read_notes",           "kind": "local_kb",     "external_io": false },
    { "name": "write_note",           "kind": "local_kb",     "external_io": false },
    { "name": "run_shell",            "kind": "shell",        "external_io": true }
  ]
}
```

关键字段：`kind`（行为大类）和 `external_io`（是否允许把数据送出本域）——这两项就是后期能"硬判"的最小抓手。

### B. 政策 → 规则（把自然语言变成条件）

以《三级信息政策》里踩坑的旧句式为例，逐条转成规则模板：

```python
# policy_rules.yaml（简化示意）
rules:
  # 规则1：若某条政策未声明任何可用工具，则该声明必须与"可调用能力白名单"一致
  #   反例（踩坑根源）：旧提示词"只依据资料回答"隐含 tools 白名单为空，
  #   后来却悄悄多出 web_search —— 白名单没跟着涨，就打架了。
  - id: TOOL-ALLOWLIST_SYNC
    desc: "凡在提示/政策中声明了 tool 约束的，其可用工具集合必须 ⊇ capabilities 中声明的该角色数据集"
    check: |

  # 规则2：禁止 external_io=True 的能力接进标注"仅内部使用"的政策作用域
  - id: IO-BOUNDARY
    desc: "external_io 能力不得出现在标注为 local-only 的 policy scope 内"
```

> 落点：把这些写成 CI 里跑的 schema / 逻辑断言（比如用 JSON-schema 校验 capabilities.json，再用一段脚本遍历 policy scope 与能力白名单做子集校验）。有任一 diff 未同步即红掉，CI 失败拦住合入。

### C. 一条通用 SQL 式警觉

规则颗粒度越细越难维护。够用就行——**先抓两类最常翻车的硬冲突**：
1. **能调用了吗**：政策声明的能力白名单 与 实际注册工具集合 是否子集一致；
2. **数据能出去吗**：是否把 `external_io=true` 的工具放进了标注"仅内部"的作用域。

其余语义软冲突全部下沉给第 3 层。

## 第 3 层：评测集驱动的语义回归用例构造

不是看一句话，而是**观测 agent 的信息路径（调用序列）是否守住政策本意**。

### A. 用例骨架（每条政策 3 例：正例 / 反例 / 边界）

```jsonc
// eval_case.json
{
  "policy_id": "三级信息政策·资料优先",
  "intent":    "资料里能答 → 用资料；资料答不了但工具有 → 调工具；都没有 → 通用知识并标注",
  "cases": [
    { "role": "positive", "scenario": "资料含答案，工具也开着", "expect_path": ["read资料"], "fail_if_asks_permission": true },
    { "role": "negative", "scenario": "资料没答案，但 web_search 能取到", "expect_path": ["调用tool"], "note": "踩坑复现：模型宁可问许可也不调 tool → 此例用来抓住再犯" },
    { "role": "boundary", "scenario": "资料、工具都没有答案", "expect_path": ["通用知识回答"], "expect_flag": "must标注来源" }
  ]
}
```

### B. 判定方式：记录"信息路径"，别只看最终文本

给被测 agent 挂一层**调用追踪探针**，记录它实际走了 read / tool / 直接答 的哪条路，再与 `expect_path` 比对：

- 只看文字容易误判（可能嘴上说"我查一下资料"其实没调工具）；
- 看调用序列 + 是否 ask_permission，能击穿上文 M5 那种"装乖不干活 / 不敢动"的假通过。

### C. 用例设计提醒（这条最容易偷懒）

- **正例、反例、边界例都要造**，只造正例会让系统自我感觉良好。
- **故意放一个"踩坑复现"用例**：把历史上真实踩过的坑（如 M3 提示词 × M5 工具）做成一劳永逸的回归锚点，防止"老问题借着新能力复活"。
- 跑分产物收敛成 **golden set**，作为每个里程碑固定的政策健康基线，方便对比折线。

## 落地顺序建议

先上第 1 层（diff 门槛，立刻止血）→ 再加第 2 层静态断言（CI 兜底"忘复查"）→ 最后攒第 3 层 golden set（验行为语义）。成本逐步升高，价值也逐步加深。
