# 047 DSML 泄漏降级：截断保正文 + 明确故障告知，不建第二套解析器

> 状态：**已批准（2026-09-26）**，用户裁定甲案「截断 + 明确故障告知」+ 修完「再跑一轮双臂实机出分」（AskUserQuestion 两问）｜日期：2026-09-26
> 授权出处：用户 2026-09-26 对「重试 2 次全无效后那条消息怎么处置」的选择；[046 遗留章节](046-frozen-real-task-eval.md#遗留dsml-泄漏需另案047)；原始记录见 [033](033-s6c-orchestration.md) 实机验收**发现 B**
> 前置事实：[033] 已建处置链（不入底片 + 提示重试上限 2 次 + 超限「诚实降级」原样返回）；[046] 的冻结评测把它照出两个新毛病——交付守卫判红、LLM-judge 被骗满分

## 背景与动机

033 立的「诚实降级」当时是对的方向：**无药可救时把原样吐给用户，好过装作没事**。但 046 的冻结评测第一次给了它可量化的读数，暴露出「原样」这个选择本身有两笔代价：

1. **用户拿到的是不可读的内部格式串。**`loop.py:160-161` 把最后一次泄漏消息按普通回答返回，这条消息既进最终回答也进底片。用户看到的是 `<｜｜DSML｜｜ calls>` 开头的一坨标记，得自己从 `parameter name="summary"` 里刨内容。
2. **评测仪器被它骗过一次。**`finish_plan` 的长 `summary` 参数里装着完整的收官陈述，judge 读参数就给了 **5/5**——一条**工具根本没执行、计划板没关闭**的回答拿了满分。这不是 judge 的错（046 已把「judge 必须有地面真值」立为拍板③），但它说明「原样保留」在自动化评分下会被读成成功。

更要紧的是第三条：**这个故障不是罕见边角**。三轮冻结评测（8 份落盘出分记录）里复现 **8 次**，其中 `finish_plan` 占 4 次——恰好是最该正常收官的那一步。重试 2 次全部无效，说明它是同参数形态下的稳定故障，不是抽样噪声。

## 地面真值：真实泄漏样本有两型

修法必须对着落盘的真实样本设计，不能凭想象。从 `data/evals/frozen-2026*.json` 取到 8 条：

| # | 出分记录 | 场景 | 型 | 泄漏的调用 |
|---|---|---|---|---|
| 1 | `055033Z` | r1-research-report | 纯 markup | `web_search` ×2（正文全在 `query` 参数） |
| 2 | `055033Z` | r4-multistep-todo | 纯 markup | `update_plan_step`（step_id/status/note） |
| 3 | **`061616Z`** | **r1-research-report** | **混合型** | `write_note`（**前半是完好的五日行情表 + 周变动分析**，「现在写入笔记：」之后才接泄漏调用） |
| 4 | `061616Z` | r4-multistep-todo | 纯 markup | `finish_plan`（长 summary） |
| 5 | `065045Z` | r4-multistep-todo | 纯 markup | `list_notes`（空参） |
| 6 | `070300Z` | r2-plan-research | 纯 markup | `finish_plan`（长 summary） |
| 7 | `070827Z` | r2-plan-research | 纯 markup | `finish_plan`（长 summary） |
| 8 | `071302Z` | r4-multistep-todo | 纯 markup | `finish_plan`（长 summary） |

markup 形态（全角竖线）：

```
<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="finish_plan">
<｜｜DSML｜｜ parameter name="summary" string="true">…正文…</｜｜DSML｜｜ parameter>
</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
```

**混合型（#3）是本案的设计约束**，它一刀否掉两个看起来最省事的方案：

- 「从第一个标记起全截断、不保留任何正文」→ 会毁掉 #3 前半那张完好的行情表，把一次局部故障升级成整轮零交付。
- 「只用正则剥掉标签、保留中间文本」→ #3 里 `write_note` 的笔记正文会被当成已交付的回答留在 content 里，而**笔记一个字节都没写进库**。这是把失败伪装成成功，与 033「不装作没事」的原则正面冲突。

## 选项

### 甲：截断 + 明确故障告知 ← **裁定**

保留第一个标记之前的正常正文（救回混合型的前半），标记之后整块丢弃，替换为一句明确告知，并从 `invoke name="X"` 正则提取丢失的工具名写进告知。同时经 `on_text` 外发，使流式视图与落盘尽量一致。**不建解析器。**

代价：纯 markup 型（7/8）会变成「几乎空正文 + 告知」，`finish_plan` 长 summary 里的内容确实丢了——但**丢得诚实**，且交付守卫从「裸格式串」变成可判定的诚实降级。

### 乙：只剥标签，保留参数文本

纯 markup 型看起来「内容都还在」，评分最好看。**被混合型样本否掉**：未执行成功的调用参数会冒充交付物。这是拿分数换诚实，方向反了。

### 丙：解析泄漏文本并补执行

唯一能真正救回 `finish_plan` 收官（计划板正常关闭、summary 不丢）的方案。**否决理由两条**：① 等于在解析层之外维护第二套 tool-call 解析器，格式脆、模型一变就废；② 执行的是「解析层已经拒绝过的意图」，安全面变大——注入载荷若能走这条路径，就绕过了正常解析链的全部约束。033 的分层原则（解析层负责把模型输出变成合法调用，内核不越权代劳）比救回 4 次 `finish_plan` 更值钱。

### 丁：原样保留 + 追加告知

信息零丢失，但用户仍拿到一串内部格式标记，评测交付守卫照旧判红，r4 的「交付失败」不会改善。只解决了「不装作没事」，没解决「不可读」——而 046 照出的正是后者。

## 拍板

### 1. 降级点只有一处，改的是「返回什么」不是「什么时候返回」

`_merge_with_leak_guard` 的重试上限、独立计数、不入底片、提示注入投影——**全部不动**（033 的处置链是对的，046 也没质疑它）。只在 `leaks > _DSML_LEAK_RETRIES` 那一行把 `return reply` 换成 `return _salvage_dsml_leak(reply)`。两个调用点（工具循环 `loop.py:447` / max_rounds 收尾段 `loop.py:490`）自动同时受益，不分叉。

### 2. 截断点 = 第一个标记出现的位置，之前的正文一字不改

`keep = content[:cut].rstrip()`。混合型的前半完好回答由此保住。`rstrip()` 是因为真实样本里标记前总有 `\n\n`（#3 的「现在写入笔记：\n\n」），尾部空白留着难看。

### 3. 丢失工具名从 markup 里正则提取，只提名字不提参数

`<｜｜DSML｜｜ invoke name="([^"]+)"` → 去重保序。**只提名字**是刻意的：参数里可能装着几百字的笔记正文（#3），把它复述进告知就等于乙案从后门回来了。用户需要知道「哪个工具没执行成」，不需要在告知里读到「没执行成的内容」。

### 4. 告知文案不得包含泄漏标记本身

否则 `_is_dsml_leak` 对返回值的语义就含糊了（虽然该函数只在 merge 后调用一次，但落盘记录里再出现标记，下一轮任何自动化扫描都会误判）。文案用「内部函数调用格式」指代，字面量一次都不写。

### 5. `on_text` 同步外发告知，但**不承诺**流式视图与落盘逐字一致

已外发的流式块收不回来（033 的 docstring 明写的 tradeoff，本案不推翻）：用户在流式里会先看到泄漏 markup 闪现，再看到告知。落盘/返回值里 markup 已被截掉。这个差异是**已知且可接受**的——缓冲整流式的替代方案要牺牲首字延迟，033 已否决，本案不重开。

### 6. 用 `dataclasses.replace` 造新消息，不原地改

保留 `usage` 字段（token 记账不能因为一次降级就丢账），也避免调用方手里已有的引用被悄悄改写。

## 判定标准

1. 三门全绿（基线 **541 passed, 2 skipped**）；既有 4 条 DSML 测试里 `test_dsml_leak_persists_degrades_honestly` 的断言必须从「原样等于样本」改为「截断 + 告知」——**这条断言的翻转是本案的直接验收物**，不是附带损害。
2. 新增离线单测覆盖真实样本三型：纯 markup 型（`finish_plan` 长 summary）、混合型（前半正文必须逐字保住）、空参型（`list_notes`，提取得到工具名）。
3. 降级后的 content **不含任何 `_DSML_LEAK_MARKERS`**；告知里**含丢失的工具名**。
4. 正常消息（无泄漏）**零改动**——半角仿制品 `||DSML||` 那条既有测试照旧通过，降级函数不在非泄漏路径上被调用。
5. 双臂实机重跑出分：r4 从「交付失败」变为诚实告知（交付守卫不再因裸格式串判红）；若 r1 复现混合型，前半行情表必须在最终回答里。

## 反方（预写）

- **「截断丢信息，用户宁可见到原文自己去刨。」** —— 部分成立。但 046 的读数显示：8 次泄漏里 7 次的「原文」是纯 markup，刨出来的是**未执行的调用参数**，不是交付物；唯一有正文可刨的 #3，其正文在截断点**之前**，甲案完整保留。真正丢失的只有「没执行成的工具参数」，而这个东西本来就不该以交付物形态出现。
- **「judge 被骗满分是 judge 的问题，不该改内核去迁就评测。」** —— 不成立。改内核的理由是用户拿到不可读的输出（判定标准 5 之外的事实），judge 被骗只是同一缺陷在仪器上的投影。若只为评分，乙案分更高——本案恰恰没选乙案。
- **「重试 2 次全无效，应该先查为什么重试没用。」** —— 成立但不属本案。046 已把「`_DSML_LEAK_HINT` 重试 2 次全无效」记为**新证据**；根因在模型侧（deepseek-flash 在长参数场景下稳定走文本通道），改 hint 措辞或提高次数都是盲试。本案只管**故障已经发生之后**的处置。根因另案，且优先级低于「用户不再拿到裸格式串」。
- **「丙案能救回 finish_plan，计划板不关闭是更严重的状态污染。」** —— 前半成立：计划板确实没关。但甲案不掩盖它——告知里明写 `finish_plan` 未能执行，用户和评测都看得见；丙案则是用一个自建解析器 + 扩大安全面去换它。若将来计划板未关闭造成实际损害，正确的修法是**让 plan 板可被下一轮自动收尾**（幂等），不是让内核代模型解析被拒绝的输出。

## 不做（防范围蔓延）

- **不建 DSML 解析器**（丙案，已否决）。
- **不提高 `_DSML_LEAK_RETRIES`、不改 `_DSML_LEAK_HINT` 措辞**：实测 2 次重试全无效，是同参数形态下的稳定故障，加次数只烧 token。
- **不缓冲整流式**（牺牲首字延迟，033 已否决）。
- **不改 `_is_dsml_leak` 的判定条件**：`tool_calls` 非空即不判泄漏，这条语义 046 没照出问题。
- **不动 `data/evals/` 里的历史出分记录**：那 8 条泄漏样本是地面真值，append-only，改了就没法复查本案的依据。
- **不为半角 `||DSML||` 等仿制品扩标记表**：既有测试已钉住「普通回答提到 DSML 字样不被拦」，扩表只会增加误伤。

### 判定标准 5 逐条核对

### 三条新读数（本轮真正的产出）

1. **甲案把「零交付」从隐形变成可见，代价是分数更低。** r2/r4 的工具全做完了（r2 轨迹 `make_plan + spawn_step×3 + list/read/search_notes + spawn_subagent×2 + update_plan_step×4`；r4 轨迹 `get_current_time + add_todo + update_plan_step×6 + list_notes`），**只有最终那句收官被吞**。judge 判 1/5 是对的——用户拿到的确实只有一句故障告知。046 首轮这两条的 5/5、3/5 是 judge 从泄漏 markup 的 `summary` 参数里读出来的**假分**。所以 full 臂质量均分 4.90 → 4.20 **不是退化，是停止自欺**：同一批故障，以前记 4~5 分，现在记 1 分。
2. **泄漏点会漂移，不固定在收官那一步。** 作废轮（见下）r2/r4 泄漏 `update_plan_step`、r1 泄漏 `web_search×2`；本轮 r2/r4 泄漏 `finish_plan`、r1 不泄漏。8 条历史样本 + 本轮 2 条 = `finish_plan` 仍占多数，但**不能靠「只在收官处防」来修根因**。
3. **`spawn_step` 焊点本轮自己接上了。** r2 轨迹含 `spawn_step×3`，[046 读数 3](046-frozen-real-task-eval.md) 记的「模型绕开 `spawn_step` 退回手工桥」**本轮未复现**（r2 判红的原因换成了泄漏）。这正好是 046「禁止用单次出分驱动机制改动」纪律的用例：那条已知问题的证据基础从「三轮均判红」退为「非确定性复现」，不能据此下线 `spawn_step`。

### 附带修掉的仪器缺陷：被测副本的 `src` 来自 HEAD

本轮**先白烧了一次 ¥0.7362**：第一次重跑后 r1/r2/r4 照旧判「泄漏内部调用标记」，dump 落盘 `answer` 发现裸 markup 原样俱在——修改压根没进被测副本。根因：`worktree.py:71` 的 `create_worktree` 是 `git worktree add <dir> -b agent/<name>`（**从当前 HEAD 切**），而 `frozen_eval._prepare_worktree` 只补 `data/vector_db` 与 `evals/scenarios`，不补 `src/`。未提交的机制改动对被测副本不可见 → **分数照旧却以为改动生效了**。

修法：`_prepare_worktree` 开头 `shutil.copytree(REPO_ROOT / "src", wt / "src", dirs_exist_ok=True)`，离线测试 `test_prepare_worktree_overlays_working_tree_src` 钉住。连带自查 [046](046-frozen-real-task-eval.md) 是否说过假话：`git diff --stat HEAD -- src evals` 显示当时未提交的 `src` 改动只有 `terminal.py` 一行 `errors="replace"`（SSRF 栅栏在评测器**父进程**侧，确实被测到了），故 046 的结论无需更正，但其「保真度偏差 1」自本轮起失效。

### 遗留（本案不解决，且甲案明确不承诺解决）

**泄漏根因未修**：纯 markup 型（历史 8 条里 7 条）截断后只剩告知 = 整轮零交付。甲案的承诺边界是「用户不再拿到裸格式串 + 故障可见」，不是「救回交付物」——丙案（解析补执行）已否决，理由见选项节。触发信号 = 泄漏频次继续上升，或计划板未关闭造成实际损害（届时正确的修法是让 plan 板可被下一轮幂等收尾，见反方第 4 条）。

**同时更正本案两处归因**（原文留档不改写，更正记在这里）：

1. **反方第 3 条的「根因在模型侧（deepseek-flash 在长参数场景下稳定走文本通道）」是错的。** 056 从 17 条落盘样本取出丢失工具名分布：`list_notes`（**空参数**）与 `read_file`（**短参数**）同样泄漏 ⇒ 与参数长度无关。真根因在我们自己的请求里：收尾段恒发 `tools=None`，模型想调工具时**结构上无法**产出 `tool_calls`，只能走文本格式。
2. **「重试 2 次全无效 = 同参数形态下的稳定故障，不是采样抖动」这个解释也要换。** 事实成立，但原因是 `_merge_with_leak_guard` 重投时 `tools` 参数不变（仍是 `None`），而 `_DSML_LEAK_HINT` 要求「通过标准 tool_calls 字段发起」——**一条结构上不存在的出路**。故「不提高 `_DSML_LEAK_RETRIES`」这条「不做」的结论不变，理由换成：出路不存在时，重试多少次都不存在。
3. **样本计数从 8 条更正为 17 条**：本案只扫了裸 markup 型；甲案上线后泄漏被降级成告知文本、markup 已被截掉，需靠告知里的工具名反查才能扫全（056 的表是全量）。恒等式证据也在那时才出现：**9 条无 spawn 的样本 `llm_calls` 恒等于 8 = 5 轮 + 1 收尾 + 2 重试，无一条 < 8** ⇒ 泄漏只发生在收尾段，从不在工具循环内。
