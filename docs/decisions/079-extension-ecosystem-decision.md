# ADR 079：扩展生态只开外部进程接口——不做 in-process Python 扩展

- 状态：**已批准**
- 日期：2026-10-05
- 立项出处：[competitive-roadmap P2-3](../internal/competitive-roadmap.md)（扩展生态决策）
- 关联：044（记忆层 MCP 化——本案把其「加出口不改内核」从记忆层推广到全扩展面）、048/049/050/052/057（安全围栏族——in-process 对它们零效力）、073 之前的 P1-6（sandbox profile 正交旋钮）

## 背景

roadmap P2-3 原文点的是两派：Pi（TS 扩展**进进程**）vs Claude Code
（hooks + MCP **外部进程**），要的是「做决策而非做实现」。但这条案
到动手时已被**部分提前**：044 把「记忆层 MCP 化」提到 P1 落地（A 径，
只读两工具），8.6 对外分档收窄。所以 P2-3 剩下的问题不是「要不要
MCP 化」（已做），而是整个扩展生态的**形态**——my_project1 是开放
in-process Python 扩展，还是只开放 MCP/hook 外部接口。

现状盘点（Grep + 目录核对）：

- 扩展面**已经全是外部进程**：`servers/` 四件
  （`memory_server`/`notes_server`/`sdk_server`/`http_demo_server`）
  全是 stdio 子进程，`mcp_servers.json` 配置化挂载；
- **无任何 in-process 插件机制**：无 `importlib` 动态加载、无
  `entry_points`、无插件注册表——in-process 扩展是零代码、零消费者。

## 选项

- **A. 只开外部进程接口**（MCP stdio 服务器族 + 未来 hooks 作为确定性
  外部闸门）：安全边界清晰，与 P1-6 同一张地图。现状已 ~90% 在此。
- **B. 开 in-process Python 扩展**（Pi 式：第三方代码 `import facta`
  跑进 agent 进程）：安全边界模糊，且要另建一套隔离才配得上它。
- **C. 两者都做**：先把 A 的缺口补齐、等真需求再评估 B 的入场券。

## 拍板

**A。B / C 不做。**

### 1. 主论据：in-process 与「经模型之手调工具」是两种威胁模型

现有全部安全设施——048 seatbelt 写围栏、049 凭证读围栏、050 内容闸、
052 记忆写围栏、057 计划范围闸——的语义都是「**程序单方面对模型意图
设防**」。第三方 in-process 代码**自己就是程序**：它直接
`open(env)`、`import` 任意模块、`mutate` agent 内部对象，上述围栏对它
零效力。要安全就得另建一套插件沙箱/隔离，那是 P1-6 container 档的
量级——为一个**零消费者**的能力先建它，是 ponytail「砍过度工程」+
032「文件数>10 才加配置」同款死旋钮教训。

而外部进程接口**免费复用已建的全部设施**：MCP stdio 服务器就是普通
子进程，读侧走 `read_learned`/`render` 单份真值（044 已钉），若要写
侧将来走与内部工具同款的审计/沙箱纪律。安全边界就是「一个外部进程 +
一套 stdio 协议」，与 P1-6「执行隔离 × 确认策略正交」同一张地图。

### 2. 数据护城河不依赖 in-process

8.3 终极检验的答案是「记忆**数据** + 开放格式（Markdown 行格式，
pi-mem/pond 同构）+ 一个**存在的接口**（044 只读 MCP）」，与「第三方
代码能否跑进进程」无关。刺 #9 的解（MCP 化提前到 P1）已经兑现——
**可插拔是「接口可插拔」，不是「进程可插拔」**。in-process 对「换
harness 带得走记忆」这件事不贡献任何东西。

### 3. 与 044 的「破例」自洽，且方向一致

044 已裁定记忆层「加出口、不改内核、读走单份真值」。外部进程接口
就是把这条裁定从记忆层**推广到全扩展面**。反过来，in-process 扩展会
逼内核暴露出「可被第三方代码 import 并 mutate」的内部形状，与
043/042/044 反复强调的「单份真值源」纪律相反——第三方 in-process
代码绕过 `read_learned` 直接 `open()` 就是第二个真值源，漂移的那天 =
对外读到与内部不一致。044 破例 import facta 源码**是唯一被允许的
「进口」**，且被限定在服务器进程内、按纪律消费，不是「放开进程内
自由 mutate」。

### 4. 零消费者

roadmap 8.4 三信号（被吞并/被排挤/被锁死）一个未兑现，044 反方 1
「没有第二个用户」对 in-process 同样成立——今天没有任何人来问「能不能
在进程里挂我的扩展」。为它建加载器 + 沙箱是提前建设。

## 负决策（明确不做）

- **不做 in-process Python 扩展**：不加 importlib 动态加载 / entry_points /
  插件注册表；不给第三方代码「import facta 并在进程内 mutate」的官方
  通道。
- **不做 hooks 槽位（P0-1）**：现状前提脱节（architecture 活清单 297：
  本项目当前不是 coding agent，五条触发信号结构上不触发）；且 hooks
  是「确定性**事件闸门**」（ADR-038），不是「第三方**能力注入**」——
  与「扩展生态」是两件事，别混为一谈。等前提兑现再单独开案。
- **不把 MCP 只读升级为写**（044 已裁定）：074 已把 tombstone 落地、
  053 已把 provenance 落地，写路径开闸只差「真实消费者」这一个条件，
  不预先开。
- **不写对外文档 / 不承诺 API 稳定**（044「不做」延续）。

## 正面（被认可的扩展面，现状即答案）

- **MCP stdio 服务器族**（`memory_server` 只读 / `notes_server` /
  `sdk_server` / `http_demo_server`），外部 harness 经
  `mcp_servers.json` 挂载。
- **治理三纪律**（044 确立，本 ADR 推广为全扩展面纪律）：
  ① 读走单份真值（import facta 源码复用 `read_learned`/`render`/
  `CATEGORIES`，服务器内不自建 `open()`）；② 挂载即授权（用户写配置 =
  同意，不加 `allow_user_scope` 类死旋钮）；③ 写路径不开闸直到撤销
  语义（tombstone）+ provenance 齐备。

## 边界（诚实登记）

- 外部进程接口目前是「**只读 + 纯出口**」：`memory_server` 只读、内部
  agent 不消费它（044 拍板 4）。「外部 harness 读走记忆并反哺」的闭环
  缺写路径——那是 tombstone（074 ✅）+ provenance（053 ✅）+ 真实消费者
  三条件里的**最后一个**还没兑现，不是本 ADR 的疏漏。
- 外部进程有启动成本（子进程 + 探活），不适合高频每轮调用——所以记忆
  注入仍走内部直读快照（044 拍板 4），外部接口只做低频挂载。
- hooks「确定性外部闸门」这条线被**刻意留白**：本 ADR 拒绝的是「现在
  建 in-process / hooks」，不是「永久不建」。写清区分是为避免将来把
  「扩展 = 外部进程」误读成「扩展 = 只读 MCP、再无其他」。

## 验收

ADR 落定 + 负决策说明（纯决策项，无代码、无三门）。

## 触发信号

- **in-process 重开**：出现真实使用者明确要求「在进程内挂我的扩展」，
  且给出「外部进程做不到」的硬理由（性能/内存共享）——届时先兑现
  P1-6 container 档的隔离能力再谈 B，不是现在预建。
- **MCP 写路径开闸**：外部 harness 实机来问「能不能写」（044/8.6 撒饵
  信号②的更强形态）——tombstone（074 ✅）+ provenance（053 ✅）已齐，
  只差这一个真实需求。
- **hooks 开案**：前提兑现（VS Code 壳立项 / 编码类任务成为常态），
  且与扩展生态分开立项、单独走 ADR。
