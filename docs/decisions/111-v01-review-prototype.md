# ADR 111：V01 最小原型——指定仓库的开工前方案评审

- 状态：**方案已定，实现与验证待完成**（2026-10-18）
- 日期：2026-10-18
- 上游：[098](098-product-prototype-priorities.md)（D01 方案评审与范围控制）、
  [110](110-product-validation-and-engineering-showcase.md)（V01–V04 验证顺序与接入要求）、
  [014](014-product-positioning.md)/[021](021-direction-decisions.md)（执行与长期记忆主线）、
  [107](107-ide-context-inbox.md)（IDE 上下文桥边界）。
- 调整关系：落实 `098/D01` 与 `110/V01` 的最小原型；只定实现落点与首版边界，
  不改写 098/110 的方向裁定，不把方案定稿记成原型已交付或需求已验证。

## 背景

098 已选「开发方案评审与范围控制」为首个产品切口，但原型与验收未完成；
110 把验证顺序改为 V01 最小原型 → V02 少量自用 → V03 外部探索 → V04 案例与
去留，并对 V01 提出硬要求：**必须解决「用户明确指定被评审仓库」的接入**，
读取范围限制在所选项目、项目记忆归属明确、不通过放宽全局文件权限解决接入。

读码基线 `8b31672`：`orchestrator/assemble.py` 把主 Agent 的文件锚点
`workspace_root` 绑定到 `paths.WORKSPACE_ROOT`（Facta 本仓）；107 的桥只投递
路径与选区，不能据此声称已具备读取外部仓库的能力。因此 V01 的首版工作集中在
「把评审跑起来 + 能读用户指定的仓库」，复用既有的装配/锚点/记忆/记账能力。

## 裁定

### 1. 入口：Web 评审页（FW 第六页）

新增 `/review` 页面（浏览器可视化入口），表单为**分节材料文本 + 被评审仓库根
路径**，提交后显示短评审。前端走 `POST /api/runs/sync` 同步端点（一条往返拿
完整结果），复用既有 run 机制，不新建引擎、不新建任务框架。

- 评审在**独立新会话**里完成——材料与评审都落在会话文件里，来源可追溯。
- 提交参数 `mode="review"` 与 `repo_root` 只在评审路径生效；缺省 `mode="chat"`
  使全部既有调用方（CLI、github_bot、评测、headless 脚本）逐字节不受影响。
- 参数、界面与模块划分以本条为准；后续若要改形状另立 ADR。

### 2. 接入：复用锚点注入缝，不放宽全局权限

被评审仓库的接入**不新建通道、不放宽全局文件权限**，而是复用 S6a 已有的
锚点注入缝：`register_file_tools` 在注册时按 `ctx.workspace_root` 闭包捕获锚点
（`tools/files.py`），评审 registry 用 `replace(mother_ctx, workspace_root=repo_root)`
重新注册文件工具，锚点随之指向所选仓库。由此：

- **读取范围自动限制在所选项目**——围栏（`_resolve_in_workspace`）相对
  `repo_root` 判定，`../` 逃逸、绝对路径跳脱、symlink 指外照旧被挡；
  `.env`/`.git` 等敏感黑名单同款按 `repo_root` 相对判定（读都不行）。
- `repo_root` 是外部输入，须校验「存在且为目录」再解析；不通过放宽全局权限
  或新增专用读取器来解决接入。
- 已知边界：黑名单里 Facta 专属的相对路径（如 `data/memory`）作用在外部仓库上
  可能误挡同名目录——按相对路径判定的固有代价，登记为观察，实测出现摩擦再议。

### 3. 记忆归属：项目决定只在同项目注入，评审不自动固化

- **项目决定（learned 三桶）只在 `repo_root == WORKSPACE_ROOT` 时注入**——
  即评审 Facta 本仓时才带 Facta 的已确认决定；评审外部仓库不注入 Facta 的决定，
  避免把不同项目的决定混作当前约束（110 §4）。
- 评审**不注入用户级记忆**（那是陪伴者语境，与评审无关，纯噪音）。
- **评审意见不自动固化**：review 模式跳过 `settle_session` 的记忆固化
  （consolidate 会从「材料 + 评审」里萃取 learned 条目），只做保底落盘——
  与 098「模型评审意见不自动升级为用户决定」一致。仅有经用户确认的项目决定
  才作为后续任务的约束。

### 4. 评审人设与结构约束

- 新增评审人设 `REVIEW_SYSTEM_PROMPT`（提示词=调教区，照 `github_bot/prompts.py`
  先例），人设内写明输入/输出契约、评审范围与边界。
- 评审 Agent 的 `allowed_tools` 设为**只读证据子集**
  （`get_current_time / list_notes / read_notes / search_notes / search_and_summarize /
  read_file / search_code / list_dir`），并经 `Agent.schemas()` 与 `execute()`
  双重过滤——「不改代码、不自动跑命令、不派子任务」是**结构性**成立，不靠人设
  自觉；不新建第二套 registry。
- 评审 run 不挂场景路由（`router=None`），保确定性。

### 5. 输入输出契约（沿用 098）

- **输入**：任务目标、验收要求、待评审方案、可读取的所选仓库；相关且有效的
  历史决定作为补充。允许手动粘贴材料（分节文本），不以 IDE 深度接入为前置。
- **输出**：总体判断 + 逐条〔对应需求 · 代码/文档依据 · 具体影响 · 最小修正〕；
  区分事实、推测与待验证项；允许「材料不全」与「未发现需改动的问题」两种结果；
  不设问题数量配额。
- **评审范围**：①覆盖目标/验收？是否与有效项目决定冲突；②文件/入口/命令/
  接口/状态前提是否与仓库实际一致；③每项改动是否必要、有无更小范围（不得仅凭
  改动大判定过度工程，也不得把既有纪律误判为多余）；④验证是否真覆盖改动。
- 决策反馈由用户记录采纳/驳回/待核实；评审本身不得扩充需求或形成无期限评审循环。

### 6. 首版边界

- 先做开工前方案评审；自动改代码、完整成果验收、执行期间实时监控与自动叫停
  不属于首版。要控制执行中的任务范围，必须先有相应状态接入。
- 不自动运行方案中的命令；需实际执行才能判断的事项标为「待验证」。
- 不建设 IDE、通用代码阅读器或三工具专用适配；不迁入 Qoder 工作材料。
- 独立评审通过新会话完成，不以换模型或多 Agent 投票保证正确性。
- 不提前建设通用 Agent 平台、独立 SDK 或多产品基础设施；评审会话与普通聊天
  共用会话仓库（来源追溯免费），混列出现真实摩擦时再议分目录。

## 待验收

- [ ] V01：在用户指定的仓库上完成带证据的短评审，支持「无问题」与「材料不足」
      两种结果，并验证确实读取了所选仓库（而非 Facta 仓库）。
- [ ] 评审 Agent 的工具清单确实只含只读证据集，且不自动写入项目文件或固化记忆。
- [ ] 评审 facta 本仓时注入项目决定、评审外部仓时不注入，归属口径可复核。
- [ ] 完成 1–2 个真实自用任务（110/V02），记录读仓库、准备材料、意见核实等摩擦。
