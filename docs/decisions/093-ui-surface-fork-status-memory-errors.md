# ADR 093：已有能力接用户界面——fork 入口、环境状态徽章、记忆操作失败提示

- 状态：已裁定（R07 实现方案）
- 日期：2026-10-06
- 上游：[087](087-project-review-and-next-priorities.md) R07（已有能力接用户界面）
- 推翻关系：无新增

## 背景

087 复评登记的界面缺口（原文）：

- fork API 已落地（085），当前聊天页和 Preact 页面未见对应调用入口——
  用户想「换个思路重来」得手调 API。
- 记忆编辑/删除的异常会从 API 抛出（400/404/409），memory 面板组件
  只有 `try/finally` 没有 `catch`——失败静默，busy 复位后错误消失，
  用户以为改成功了。
- 沙箱档位/审批策略只能靠读环境变量或日志确认——「现在到底跑在哪档」
  对常用操作不可见。

R07 完成标准（087 L50 原文）：「先补 fork 入口、操作失败提示、实际沙箱
状态，再展示记忆来源与召回原因；常用操作不依赖手调 API 或查日志；配置
档位与实际后端分开展示。」本 ADR 裁定「先补」三件；「再展示」后半句的
处置见边界节。

## 裁定

1. **新增 `GET /api/status`，返回三字段**：
   `{sandbox_level, sandbox_backend, approval_policy}`。level/policy 是
   **配置档**（`sandbox_level()`/`approval_policy()` 归一化结果），
   backend 是**实际后端**（`detect_backend()`：`seatbelt`/`bwrap`/`null`）
   ——两个字段分开放，满足 087「配置档位与实际后端分开展示」，配置写了
   workspace-write 而机器上没有可用后端时一眼能看出诚实降级。
   三者都是点用点读（不缓存），与 086 同款纪律：改环境变量重启进程即生效，
   端点只是如实转述。
2. **聊天页 sidebar 头部加环境徽章**（vanilla 主聊天页，`#env-badge`
   小字一行）：启动时 fetch `/api/status`，渲染形如
   `沙箱 workspace-write/seatbelt · 确认 on-request`；backend 为 null 时
   显示「无」（诚实降级的可见化）。fetch 失败静默不显示——徽章是便利，
   不该挡聊天主流程。放 sidebar-head 而非设置弹层：一眼可见、零交互成本。
3. **fork 按钮进会话行操作区，对所有会话开放（含 running）**。
   现有重命名/删除只在 `!s.running` 时渲染（在跑会话后端 409，按钮直接
   不给）；fork 不同——085 裁定 fork 只读源、当刻快照安全，后端对 running
   会话不 409，故 fork 按钮移出 `!s.running` 条件块，任何会话行都给。
   交互：点击 → `POST /api/sessions/{sid}/fork` → 刷新清单 →
   `selectSession(新 id)` 切到副本。fork 的是「换个思路重来」的入口，
   切过去才符合直觉（留在源会话会让用户怀疑有没有 fork 成功）。
4. **memory 面板错误提示复刻 notes 同款**：
   - `memory/api.js` 换装 notes 的 `unwrap`（`err.status` + 后端
     `detail` 文案），同源复刻不抽共享模块——这是第二次出现，按
     ponytail 三处相似才抽。
   - `Entry` 组件加 `err` state：`save`/`remove` 的异常 catch 住内联
     显示后端文案（400 内容为空 / 404 条目不存在 / 409 条目已变化）；
     **409 给「重新载入」按钮**（调 `onChanged` 重拉全量列表，与 notes
     的 409 重载同款）；404 提示后同样可重拉。
   - 样式复用既有 `.notes-banner` 族（fw 页共享 style.css），不新增
     设计词汇。

### 为什么不是 toast/通知中心

全局 toast 组件四个面板页都用得上，但那是「为假设的未来需求设计」——
当前只有 memory 一页缺错误提示，内联 banner 已够。第三处出现时再抽。

### 为什么徽章不放 fw 四页

fw 页（tasks/memory/graph/notes）各有自己的头部结构，逐页加徽章是四处
重复。环境状态是「聊天下棋时想瞄一眼」的信息，主聊天页 sidebar 是唯一
常驻外壳；fw 页要看状态点回聊天页即可。触发信号：用户在 fw 页里实际
产生过「现在哪档」的疑问。

## 边界（显式记录）

- **记忆来源**：`visible_text` 保留的可见 tag（`[已验证]`/`[手改]`）
  随 content 一起进面板，来源信息天然已可见——此项无需新工作，登记为
  「已满足」而非「不做」。
- **召回原因**（075 的 `recall_xray.jsonl`）：只有落盘、无 API。做成
  面板功能需要新查询面（按条目反查哪次召回命中、为何命中），本项不做。
  触发信号：出现「这条记忆为什么被想起来」的真实调试需求，或 R06 消融
  验收需要对照召回链路。
- 徽章只在启动时拉一次，不跟随运行期环境变量变更（进程内改档本来就要
  重启才生效的部分占多数，轮询不值当）。
- fork 按钮无 confirm 弹窗：fork 是无害只读源操作，成本是磁盘上一份
  副本，误触点掉/删掉即可，不值得一道确认。

## 验收（087 的 R07 完成标准，逐条）

- [x] fork 入口：会话行（含 running）有 fork 按钮，点击后切到副本。
- [x] 操作失败提示：memory 编辑/删除失败内联显示后端文案，409 可一键
  重新载入。
- [x] 实际沙箱状态：`/api/status` 返回配置档与实际后端两字段，sidebar
  徽章可见。
- [x] 配置档位与实际后端分开展示：`sandbox_level` 与 `sandbox_backend`
  是两个字段，徽章文案两级都渲染。
- [x] 常用操作不依赖手调 API 或查日志：fork、环境查看、记忆改删的
  失败感知全部进 UI。
- [x] 三门全绿；前端改动经 `npm run build` 重建 fw 产物。
