## 背景

用户希望同时实现三个目标：Facta 成为自己持续使用的工具、积累开源影响力、
验证外部用户需求。当前尚无外部用户，日常使用集中在 Trae、Kimi Code、
Qoder 等 AI 开发工具。Qoder 用于工作，其项目材料不作为本轮跨工具验证输入。

用户报告的具体摩擦如下，原因仍需逐例核实：

| 摩擦 | 待验证的需求 |
|------|--------------|
| 需要花很长时间 brief，以前做过的任务仍容易出错 | 少重复解释，复用有效的项目背景与决定，并检查是否被遵守 |
| Kimi Code 给出孤立代码片段，阅读时难以理解上下文 | 源码定位与讲解联动，能够沿真实调用链理解代码 |
| 使用 Trae 时需邀请外部评审，防止项目跑偏 | 独立核对方案是否符合目标、项目约定与实际代码 |
| 复杂任务可能被进一步复杂化，有时执行一天 | 控制不必要的范围，区分范围膨胀与必要工作执行失败 |

这些摩擦来自用户自己的开发流程，比尚未接触的行业场景更适合作为首个切口。
产品验证顺序为：自用任务产生实际收益 → 整理可公开案例 → 邀请少量外部试用。
影响力不足不是已确认的唯一获客障碍，仍需区分价值表达、使用门槛与需求问题。

## 裁定

### 1. Facta 作为能力底座，先验证 AI 开发中的具体环节

首批目标用户是自己负责项目方向、经常委派 AI 开发、需要亲自判断方案和结果的
个人开发者。首个产品承诺为：

> 结合项目实际检查 AI 开发方案，指出有依据的遗漏、偏离和不必要的工作，
> 帮用户更快决定是否开工、需要修改什么。

复用 Facta 已有的文件读取、检索、记忆、来源追溯与模型接入能力。先通过现有
入口验证一次完整评审，不提前建设通用 Agent 平台、独立 SDK 或多产品基础设施。
现有个人助手仍可作为自用入口，首个原型不要求用户替换其开发工具。

### 2. 三个候选按以下顺序推进

本表是**产品原型内部的先后顺序**，不与 097 的工程 P0/P1/P2 混用。

| ID | 顺序 | 原型 | 首要收益 | 排序理由与推进条件 |
|----|------|------|----------|--------------------|
| D01 | **第一优先** | **开发方案评审与范围控制** | 提前发现跑偏、遗漏或不必要的工作 | 用户已反复主动找外部评审，有明确使用行为；先验证有依据的意见是否值得其准备和核实成本 |
| D02 | **第二优先** | **项目 Brief 生成与历史决定复用** | 减少重复解释和手工补背景 | 有明确痛点且匹配记忆积累；需要与手工 Brief、项目说明文件比较，验证正确复用而非仅增加上下文长度 |
| D03 | **第三优先** | **源码联动的代码讲解工具** | 提高代码理解程度和源码定位效率 | 涉及不同的阅读交互；先区分分步解释即可解决的问题与必须依靠源码联动界面的问题 |

第一轮只做 D01 的最小原型。D02、D03 保留候选身份，不并行建设三套产品。
若真实任务表明其他候选收益更大，可以用新证据调整排序，不因底座已有某能力
就认定该能力必须成为首个产品卖点。

## D01 最小原型

### 输入与输出

- **输入**：用户的任务目标、验收要求、待评审方案、可读取的项目仓库；
  相关且有效的历史决定作为补充。允许手动粘贴材料，不以 IDE 深度接入为前置。
- **输出**：一份短评审，给出总体判断与影响本次交付的问题。每条意见说明
  对应需求、代码或文档依据、具体影响，以及最小修正建议；明确区分事实与推测。
- **材料不全**：标出无法核实的部分，继续评审能核实的内容；不补造缺失要求。
- **没有问题**：允许明确返回未发现需改动的问题，不设问题数量配额。
- **决策反馈**：由用户记录采纳、驳回或待核实及理由。只有经确认的项目决定
  才作为后续任务约束，模型的评审意见不自动升级为用户决定。

### 评审范围

1. 方案是否覆盖任务目标与验收要求，是否与当前有效的项目决定冲突。
2. 文件、入口、命令、接口和状态等前提是否与仓库实际一致。
3. 每项改动是否有必要，是否存在能达成目标的更小范围；不得仅凭改动大或
   耗时长判定过度工程，也不得把已有项目纪律误判成多余工作。
4. 验证方法是否真正覆盖改动，是否把局部检查扩成无必要的系统联调。

影响交付的问题与可选建议分开表达；无关的优化不进入本次任务。评审本身
不得不断扩充需求、追加新路线图或形成无期限的评审循环。

### 首版边界

- 先做开工前方案评审；自动改代码、完整成果验收、执行期间实时监控和
  自动叫停不属于首版。要控制执行中的任务范围，必须先有相应状态接入。
- 不建设 IDE、通用代码阅读器或三个工具的专用适配；不迁入 Qoder 工作材料。
- 不自动运行方案中的命令；需要实际执行才能判断的事项标为待验证。
- 独立评审可以通过新会话完成，不以换模型或多 Agent 投票保证正确性；
  结论依赖可核对的证据，模型判断不替代实际测试与用户取舍。
- 复用已有能力，具体入口和模块划分留给实现方案；本次仅归档方向与验收
  口径，尚未实施原型。

## 已有观察及其边界

本轮用 Facta「任务列表按状态筛选」方案做过一次人工参与的独立评审：

- 主体方案限于前端，未发现明显过度工程。
- 读码确认了可修正的执行细节：构建工作目录应为 `frontend/`（仓库根可用
  `npm --prefix frontend run build`）；正式任务页入口为 `/tasks`。
- 指出了直接复用 `.graph-chip.off` 删除线样式的交互风险，并建议用固定
  API 响应验证筛选，减少真实制造失败、审批和取消状态的准备成本。

这是一条初步观察，**不是 Facta 原型的跑分结果**。原始任务说明未完整提供，
未实施方案或实测节省时间，用户是否采纳各条意见也未记录。它支持继续验证
方案核实的价值，但尚未证明能防止长任务膨胀，也没有证明长期记忆的增益。
096 的内部消融结果同样不能直接代替本场景的收益和外部需求证据。

## 验证与后续裁决

先用 **5 个真实自用任务**验证 D01，覆盖小功能、修复及一次较复杂的方案；
材料来自 Facta 或其他可用于验证的个人项目，不人为植入错误来确保评审有产出。
先保留原始目标与方案，再评审并记录反馈。历史任务回放与新任务分开标记，
避免把已知结果造成的优势当成实际节省。

对照为用户现有做法：自己整理背景并邀请外部 Agent 评审。若可在同一任务上
获得两份评审，使用相同输入并尽量独立进行；不能对照时如实标明，不能把估计
的节省时间写成实测结果。不因原型有输出就认定它优于普通评审提示词。

每次最少记录：

| 记录项 | 用途 |
|--------|------|
| 准备材料、等待、阅读与核实意见的时间 | 分开看人的投入与总耗时，识别是否只是转移工作 |
| 有证据支持且被采纳的意见，以及对应方案修改 | 判断是否改变了实际决策；问题数量本身不代表收益 |
| 误报、重复建议、需补背景之处及处理成本 | 防止评审制造额外负担，识别 D02 是否应提前 |
| 可观察的返工、执行结果；未执行则注明 | 不把预测的“避免一天返工”当成事实 |
| 下一次相似任务是否愿意继续使用，及理由 | 判断是否形成复用动机 |

完成 5 例后形成一次去留记录：有可核实的决策收益、使用负担可接受且用户
愿意复用，则继续 D01；若收益主要受整理背景拖累，优先验证 D02；若方案
评审价值有限而代码理解摩擦更强，重排 D03。收益不足时允许暂停，不以继续
加功能替代判断。这是原型选择，不能据此宣称市场需求或付费意愿已验证。
