# ADR 092：同步任务接口的等待预算——超时、可追踪、不代裁决

- 状态：已裁定（R05 实现方案）
- 日期：2026-10-06
- 上游：[087](087-project-review-and-next-priorities.md) R05（补同步任务接口超时与确认语义）
- 推翻关系：部分推翻 [081](081-headless-json-output.md) 负决策「不设超时参数」
  （081 其余裁定全部保留，尤其「不自动裁决 L2 确认」）

## 背景

`POST /api/runs/sync`（081）用无超时 `_settle_done.wait()` 阻塞请求线程。
挂起的两种真实形态：

1. **L2 确认挂起**：headless 无批准人，`request_confirm` 阻塞到裁决或取消
   ——没人裁决也没人取消，请求就永远挂着（081 诚实登记为「边界」）。
2. **长任务**：任务正常跑几十分钟，调用方线程池槽位一直被占。

081 当时不定超时的理由：「超时语义依赖消费者对任务时长的假设，现在定不下来」。
087 复评后授权重估：问题不是「默认值定多少」，而是**调用方根本没有表达
等待预算的通道**，也没有区分「我等够了」和「任务死了」的契约。

## 裁定

1. **超时是调用方的等待预算，做成 `/api/runs/sync` 的查询参数**
   `?timeout=<秒>`（`Query(gt=0)`，非法值 422）。默认 `None` = 081 原契约
   （无限等待），向后零破坏。放查询参数而非请求体：超时是「这次等待行为」
   的属性，不是「要创建的 Run」的属性——`POST /api/runs` 的
   `CreateRunRequest` 不被污染（081 拒 `?wait=true` 是拒双语义端点；
   `/sync` 本来就是等待端点，给它配预算不违例）。
2. **超时返回 200 + `timed_out: true`**，其余字段原样：
   `{run_id, session_id, status, text, timed_out}`。`status` 是那一刻的
   真实活跃态（`running` 或 `waiting_approval`）——**`waiting_approval`
   天然就是「需要人工确认」的返回行为**，状态机既有词汇，不加新状态。
   `text` 仍是 `run.reply_text`（未完成时为空串，与失败/取消同款）。
   响应恒含 `timed_out`（正常终态为 `false`）：schema 恒定，脚本好解析。
3. **超时 ≠ 取消**（087 完成标准「区分请求等待超时与后台任务取消」）：
   `wait(timeout)` 到点只让请求线程放手，**后台 Run 一步不停**。调用方
   拿 `run_id` 自己决定去路：`GET /api/runs/{id}/events` 挂流看进度、
   `POST .../cancel` 取消、`POST .../confirm` 裁决挂起的确认。
   想让「超时顺便取消」的调用方自己补一枪 cancel——两个原语各自单一，
   不揉成一个参数（揉了就拿不回「只看一眼状态」的纯粹性）。
4. **不自动批准、不降级确认**（081 红线原样保留）：headless 触发 L2 时
   如实挂起/如实超时返回 `waiting_approval`，由调用方裁决——confirm
   端点本就对任何 HTTP 客户端开放，自动化想自裁决可以，安全责任在调用方。

### 为什么不是服务端默认超时

硬编码一个全局默认（如 10 分钟）只是把「定不下来」换成「武断」：
定时任务跑 1 分钟的报表和跑 1 小时的索引重建共用同一默认值必有一边错。
默认无限 + 调用方自报预算，把假设留在唯一知道答案的地方。

## 边界（显式记录）

- 超时精度是 `threading.Event.wait` 的量级（毫秒+调度抖动），不做
  硬实时承诺——够自动化用，不够交易撮合用。
- 超时返回后 worker 线程仍在跑：调用方若既不订阅也不取消，Run 自己会
  跑到终态落终态事件，状态可从 `GET /api/runs` 列表读到——无孤儿。
- 线程池占用问题（081 已登记）不因本项消失：超时只缩短「占用时长」，
  不改「占一个槽位」的事实。触发信号维持 081 原文。

## 验收（087 的 R05 完成标准，逐条）

- [x] 明确超时返回行为：200 + `timed_out: true` + 当时真实 `status`。
- [x] 明确需要人工确认时的返回行为：`status: waiting_approval`
  （挂起中超时返回），回归测试钉住。
- [x] 调用方能拿到可追踪的 run ID：超时返回含 `run_id`，回归测试里
  拿它调 cancel 成功（追踪链路闭环）。
- [x] 区分请求等待超时与后台任务取消：超时不取消（worker 继续），
  取消走既有 cancel 端点；两条路径各有测试。
- [x] 不通过自动批准危险操作解决挂起：确认语义零改动。
- [x] 默认契约不变：无 `timeout` 参数的请求行为与 081 完全一致。
- [x] 三门全绿。
