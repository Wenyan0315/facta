# 决策记录 · 对抗机制（critic）裁定：S5 不内置，挂触发信号（2026-09-19）

> 2026-09-12 悬案的结案（answer_eval 立项时的前置问题：「要不要给 agent 加运行时 critic 子代理」——先量基线再决定，基线已出）。返回 [architecture.md](../architecture.md)

- **裁定：S5 不内置对抗机制**。证据与理由：①基线数据（answer_eval 忠实度 13/13 合格、0% 编造错误）——当前无实测痛点，与 learned 既有铁律「无具体症状时不重构」一致；②plan-then-act 的人审环节已是更强的对抗者（真直觉+全局语境；LLM critic 挑 LLM planner 在同源模型下效果存疑——020 记过自我偏好教训）；③成本位置：运行时对抗 = 每任务双倍 token+延迟；critic 的正确用法是挂在不可逆写入前（固化审查层/write_note 查重先例），不是全程监督。

- **结构性理由（核心）**：S5 Agent 对象抽象落地后，critic 从「一个机制」变「一个配置」——即 `spawn_subagent(角色=审稿人, prompt=挑刺指令, 只回传结论)`。今天加是架构改动，S5 之后加是写一个 agent.md 条目——晚做不涨价反而打折。

- **三条触发信号**：①plan 阶段 critic ← 人审 plan 的实测打回率偏高（>30%）时加「规划挑刺」子 agent；②执行时实时 critic ← answer_eval 忠实度回落，或真实使用出现「执行了但做错」案例（基线 0% 在案对照）；③评测对抗题库 ← S5 评估体系搭设时并入（对抗的正确主场是评测而非运行时——一次性成本暴露系统性弱点，与「先度量再建设」同哲学）。
