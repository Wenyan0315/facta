## 背景与判断

Facta 已有较完整的 Agent 工程底座：CLI、Web、Bot 共用装配入口，执行链路
覆盖计划、子任务、取消、崩溃恢复、审计与隔离；记忆治理覆盖来源、撤回、
过期、预算与异步固化。分层和评估中对失败、证据边界的记录值得保留。

下一阶段建议优先补数据正确性、真实任务验收与日常使用体验。后端能力推进
较快，前端入口、验收和文档同步已有欠账：fork 已有 API，但前端尚无对应
入口；记忆层已有稳定 ID，面板仍按行号操作。新增架构能力应由实际任务中的
失败和摩擦驱动。

本篇记录本轮建议及其依据，不把建议写成已实现功能。涉及既有 ADR 中明确
后置或否决的方案，开工时需记录重新裁定的理由；本次归档不改写历史决定。

### R01：已复现的 ID 复用，以及读码确认的存储风险

落点：[memory/todos.py](../../src/facta/memory/todos.py)。

`TodoStore.add` 以当前列表最大 ID 加一分配身份。临时仓库中的复现结果：

```text
add("old task") -> id=1
delete(1)
add("new task") -> id=1
```

删除最大编号或清空列表后，旧引用可能指向新任务。现有测试只覆盖删除中间
编号后不回填空洞，未覆盖最大编号删除。另有两处读码确认的风险：`_save`
直接覆盖文件；`_load` 遇坏 JSON 返回空列表。这里没有模拟真实断电或声称
已经发生数据丢失，建议补原子写入与损坏保全。

### R02：已有稳定 ID，但面板仍按行号寻址

落点：[server/app.py](../../src/facta/server/app.py)、
[memory/App.jsx](../../frontend/src/memory/App.jsx)、
[memory/learned.py](../../src/facta/memory/learned.py)。

GET 返回行号，PUT/DELETE 路由及前端操作也按行号定位；底层已有
`update_line_by_id` / `delete_line_by_id`。手动整理、坏行删除或墓碑物理回收
可能改变行号，让旧页面持有的位置失效。普通 tombstone 撤回本身保留行，
不能笼统声称每次删除都会造成错位。本次属于代码路径确认，未做浏览器并发
复现；建议覆盖整理后旧页面提交的场景。

### R03：数据目录覆盖不完整

落点：[orchestrator/assemble.py](../../src/facta/orchestrator/assemble.py)、
[paths.py](../../src/facta/paths.py)。

`paths.py` 中的 notes、learned、sessions 等走 `DATA_ROOT`；装配层的
`TODOS_PATH`、`AUDIT_DIR`、`VECTOR_DB_DIR` 仍锚定 `WORKSPACE_ROOT/data`。
退役会话的迁移源 `MEMORY_PATH` 也需单独核对，不能简单替换而丢失旧路径。

架构活清单此前已登记待办路径问题，并裁定等待安装消费者或下次装配改动。
本轮建议将其与其他遗漏路径一起提前处理；属于优先级调整建议，不冒称首次
发现，也不把本轮建议当作迁移已经完成。

### R04：请求过的文件操作被当成完成事实

落点：[memory/compressor.py](../../src/facta/memory/compressor.py) 的
`collect_file_activity`。

临时构造一条 `write_file(path="example.py")` 调用，后接同一调用 ID 的
工具结果“错误：用户拒绝了此次操作”，函数仍返回：

```text
([], ["example.py"])
```

当前实现只提取调用请求，不检查结果。摘要应依据已完成的操作记录事实，
避免后续模型误判文件已改。该修复不要求把文件清单交给 LLM 生成。

### R05–R09：使用闭环与证据补齐

- **同步接口**：[server/app.py](../../src/facta/server/app.py) 的
  `/api/runs/sync` 使用无超时的 `_settle_done.wait()`。确认通道挂起时，
  同步请求也会等待。ADR 081 已登记此边界并选择不设超时，本轮建议重新
  评估自动化调用契约；尚未进行长时间挂起实测。
- **真实任务评估**：现有记忆消融主要证明闭卷知识召回收益，不直接证明
  执行成功率收益。沿用 ADR 046 的冻结、隔离和不为分数改题纪律，任务应
  来自真实需求，避免从记忆条目反推答案。10–20 题只作为起步样本。
- **界面**：fork API 已落地，当前聊天页和 Preact 页面未见对应调用入口；
  记忆编辑/删除的异常会从 API 抛出，组件缺少对应的用户错误反馈。
- **文档与 CI**：旧 roadmap 的“下一步”仍指向已完成里程碑；README 仍有
  ADR 数量及沙箱支持说明滞后；当前 CI 主要覆盖 Python 检查，未构建前端。
- **分发**：本次没有做 wheel 干净安装，静态资源或安装路径是否有实际缺陷
  仍待验证，不能直接作为已复现 bug 登记。

## 建议执行顺序

1. **正确性修复**：R01、R02、R03，顺带完成范围明确的 R04；以针对上述
   失效场景的回归测试验收。
2. **日常可用性**：R05、R07、R08，补同步接口契约、fork 入口、错误反馈、
   前端 CI 与当前任务表。文档简单修正可随第一轮完成。
3. **验证实际价值**：日常使用中开始积累 R06 的真实任务，再做消融和基线
   对比，按失败分布决定新增能力；R09 在分发或外部接入需求出现时推进。

## 暂缓项与重新评估条件

Repo map、LSP、通用 Hooks、完整会话树、更多图谱能力继续暂缓，沿用既有
触发条件。当前 roadmap 已记录若干 coding agent 能力缺少真实使用前提，
不因竞品已有就平推。

重新排期的依据应来自实际使用：代码导航成本升高、重复类型错误、明确的
撤销请求、从指定轮次分叉的需求，或图谱质量成为任务瓶颈。下一阶段目标
是证明 Facta 在日常几类任务中稳定减少返工与人工介入。

后续落实条目时，在新的实现 ADR 与当前 backlog 中引用 `087/Rxx`，保留本篇
作为 `510fb65` 基线的评审记录，不把此处历史判断改写成事后结论。
