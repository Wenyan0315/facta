# ADR 091：摘要文件活动清单配对工具结果——只认成功，不冒充

- 状态：已裁定（R04 实现方案）
- 日期：2026-10-06
- 上游：[087](087-project-review-and-next-priorities.md) R04（修正摘要文件活动清单）

## 背景

087 复核确认：compressor.py 的 `collect_file_activity` 只扫描 assistant 消息里的
`tool_calls` 提取路径——**只看「点了什么菜」，从不核对「菜上没上」**。后果按
087 的诊断排序：被拒绝或执行失败的 write_file 仍进「已改文件」清单（摘要向
用户谎报成果，最伤信任）；失败的 read_file 进「已读文件」（下轮上下文注水）；
取消或崩溃留下的调用结果未知，一律按成功处理。实际复现：会前在 plan 模式里
被拒的 `write_file {path: package.json}` 照样出现在会话摘要的「已改文件」里。

R03（090）收口 DATA_ROOT 后，本项是路线图下一项。

## 裁定

1. **按 `tool_call_id` 配对点菜与结果**。M5 起 executor 回填
   `Message(role="tool", tool_call_id=tc.id)`，底片（session.json）字段既有，
   零持久化变更。配对第一胜（first-wins，正常流程不会重复；重复时以先到者为准）。
2. **成败判定用白名单，不用黑名单词表**：判定函数认「成功文案的固有格式」，
   其余一切（失败、拒绝、闸门、崩溃补位、未来新增的任何失败文案）自动归入
   「不算成功」。判向 fail-closed。
   - `read_file_succeeded(result, path)` ⟺ `result.startswith(f"{path}（")`。
     `_read_file` 三个成功出口（空文件 / 共 N 行 / offset 超范围）同此格式。
   - `write_file_succeeded(result)` ⟺ `result.startswith(("已新建 ", "已覆盖 "))`。
     `_write_file` 唯一成功返回的自有格式（diff/缩减注记在后缀，免疫）。
3. **判定函数放 files.py**——与文案生产者同文件，单一真值源；改文案的人
   第一眼看到判定。先例：learned.py 的 `STATUS_PREFIXES` 同样由 compressor
   import 消费。对账测试用真实 `_read_file`/`_write_file` 输出喂判定函数，
   文案漂移先红测试。
4. **结果缺席 = 未知 = 不进清单**。取消（断流丢弃结果消息）、崩溃（heal 补位
   文案 `[崩溃恢复]…`，白名单天然排除）、无 tool_call_id 的远古底片（M5 前），
   一律不冒充成功——退化为「无清单」，即 085 之前的行为，可接受。
5. **不统一用户可见文案、不加结构化标记**。生产侧各失败出口文案不动
   （白名单对文案分布免疫）；不用 str 子类或 Message 加字段（registry/executor/
   持久化/旧会话兜底全线波及，过度工程）。

### 为什么不用黑名单词表

- read_file 成功返回里嵌着用户文件内容，任何「错误：」「失败」之类前缀都
  可能撞内容（用户文件第一行就可以是「错误：」）。白名单只认「路径开头 +
  固定格式」，用户内容在路径之后，撞不了。
- 失败文案分布在五个文件十几种（files.py 九条、registry 闸门五兄弟、
  plan 范围闸、executor 并行异常、checkpoint 补位三档），黑名单词表必随
  文案演化漂移——每次都静默漏判，比不做更糟。

## 边界（显式记录）

- heal 补位文案散在 checkpoint.py 三处（三档分支），不理想但本项不并案：
  白名单方向下补位文案内容不影响判定，重构它是纯卫生问题，记入 R08 候选。
- 一轮里同一路径先失败后重试成功：两次调用各有自己的 tool_call_id 与结果，
  成功的那次入列，失败的那次自然排除——时序语义正确，无需特殊处理。
- `write_file` 的「内容与现有文件完全相同，未写入」按白名单归入「不算已改」，
  语义正确（文件确实没被这次调用改变）。
- 清单仍只覆盖 read_file/write_file 两个工具（085 既有范围），不扩。

## 验收（087 的 R04 完成标准，逐条）

- [x] 关联工具调用与结果：按 tool_call_id 配对，first-wins。
- [x] 被拒绝或执行失败的写入不进入「已改文件」：白名单判定 + 回归测试
  （确认闸门拒绝串、执行失败串）。
- [x] 失败读取不进入「已读文件」：回归测试（文件不存在、二进制拒绝）。
- [x] 取消或崩溃留下的未知结果不冒充成功：结果缺席不入清单 + `[崩溃恢复]`
  补位文案回归测试。
- [x] 对账测试钉住成功文案格式：真实 `_read_file`（三变体）/`_write_file`
  （新建/覆盖）输出必须过判定，真实失败输出必须不过。
- [x] 三门全绿；既有 `test_collect_file_activity_extracts_read_and_write`
  按新语义改写（原用例只有点菜没有结果，新语义下等于「结果缺席」，
  补上结果消息保持原断言意图）。
