# 045 learned 入口纪律：易腐事实不入库 + 冗余有对照物

> 状态：**已批准（2026-09-26）**，用户裁定走乙（提示词 + 代码闸门）｜日期：2026-09-26
> 授权出处：roadmap 8.7 消融实测（内部归档）的两个附带发现（易腐知识腐化实证 / 冗余条目）+ 8.7 末句「是否开 045 ADR 立成纪律，待裁定」
> 前置事实：消融实测已跑通（记忆注入净增量 69pp），本案是它的**副产物治理**，不动消融结论

## 背景与动机

两个发现都出自 2026-09-26 的消融实测，都是**存量数据体检**照出来的，不是设计推演：

**发现一：易腐事实会腐化，且系统无任何机制能发现。**
`other.md` 有一条 `[2026-09-17] run_turn 在 loop.py 第 113 行，该文件共 227 行`。9 天后对照现实是**第 340 行、共 501 行**——两个数字全错。腐化能存活 9 天的原因是结构性的：固化只追加（`_append` 是 `open(..., "a")`）、无校验、无过期、无 tombstone。条目每轮注入进 system prompt，模型会**当真**引用它（消融首轮就有一题因此答错方向）。

**发现二：与基础 prompt 冗余的条目，工序在原理上不可能发现。**
`other.md` 有两条（语义/逐字检索区分、历史压缩后用 search_history 查原话）被 `DEFAULT_SYSTEM_PROMPT` 逐字覆盖。冗余的代价是双份：白占每轮注入 token，且两处措辞漂移时模型拿到自相矛盾的材料。

关键诊断（纠正一个先前的误判）：**去重工序本来就存在**——EXTRACT 铁律 4「『已知记忆』里没记过吗？」、REVIEW「重复的条目只留一条」、`_harden` 批内 `seen` 去重。缺陷不在缺工序，在缺**对照物**：`_load_known` 只读 `data/learned/*.md` + `user.md`，**读不到基础 prompt**。模型手上没有那份材料，再守纪律也查不出这类冗余。

同理，易腐那条也不完全是缺纪律：铁律 4「跨会话还成立吗？」已覆盖意图，但**判定尺度模糊**——行号在「下一次会话」确实还成立，模型没判错，是纪律没给可操作的负面清单。

两个根因都落在**提示词的材料与判定标准**上，这是甲案（纯提示词）的依据；但项目既有哲学是「信模型语义，不信模型纪律」（敏感凭证就是代码级正则拦的，`_SENSITIVE_PATTERNS`），易腐事实一旦入库就是**不可逆污染用户资产**，与敏感凭证同级——这是乙案（加代码闸门）的依据。**用户裁定乙。**

## 选项

- **甲. 纯提示词**：`_load_known` 带基础 prompt + 铁律 4 补负面清单。最短 diff、零新代码路径、零误杀；但无硬边界，模型判错就入库，而入库不可逆
- **乙. 提示词 + 代码闸门**（**裁定**）：甲 + `_harden` 加易腐正则拦截。符合「信模型语义，不信模型纪律」；代价是正则脆 + 误杀风险
- **丙. 只立文档不改代码**：靠人审（记忆面板已能编辑/删除）。零风险，但纪律无自动执行点——**而这正是腐化能存活 9 天的原因**，等于不解决
- **丁. 建过期/tombstone 机制**（治出口而非入口）：真正根治腐化，但是 P2-1 另案的大工程（FR 四态状态字段），且 044 已把 tombstone 定为写路径开闸的前置。本案不抢

## 拍板

**乙。甲的两处提示词改动照做，`_harden` 加一道易腐闸门；丁不做（挂 P2-1）。**

### 1. 负面清单（提示词级，铁律 4 补一句）

一律不记，要记只记稳定部分（文件路径/名字/决定本身）：

- **行号**（「第 N 行」）
- **文件行数**（「共 N 行」）
- **git 跟踪状态**（「未跟踪」「已入 git」）
- **计数**（「当前共 N 篇」「N 条」这类会随演进的量）

理由写进提示词本身，不只写进 ADR：模型看到理由才会泛化到未列举的形态（「文件大小的 KB 数」「某函数的参数个数」同属易腐，负面清单列不全）。

### 2. 代码闸门（`_PERISHABLE_PATTERNS`，与 `_SENSITIVE_PATTERNS` 同族）

处置是**弃 + 报告里显示内容**，不是静默弃：

- **为什么不复用 P0-7 的 `candidates`**：那条通道的文案语义写死是「教训缺客观背书」，混入易腐条目会让人误判原因。两条闸门两个原因，分开报
- **为什么报告要显示内容**：易腐条目的**有用部分**（如「run_turn 在 loop.py」）值得保留，人看到原文才能剥掉易腐尾巴手工入库。静默弃 = 信息全丢
- **误杀方向**：保守偏拦。正则只匹配明确形态（`第 N 行`/`共 N 行`/`共 N 篇`/`未跟踪`），不匹配裸数字——「架构分三层」「预报窗口 7–10 天」「最多 5 条」都不含这些形态，实测不误杀

### 3. 对照物：基础 prompt 进 `_load_known`

**依赖方向是硬约束**：`agent.py`（orchestrator）已经 `from agent.memory.consolidate import CATEGORIES`（agent.py:24），所以 memory 层反向 import `DEFAULT_SYSTEM_PROMPT` 会**循环 import**，且违反分层（memory 是下层）。

裁定：**加可选参数由上层传入**——`consolidate(..., base_prompt: str = "")`，`_load_known(..., base_prompt: str = "")`。生产调用点只有一个（`assemble.py:170` 的 `settle_session`），传 `DEFAULT_SYSTEM_PROMPT`；默认空 = 现有行为，16 处测试调用点不必改。这不是死旋钮（032「零消费者的配置」那类），是**下层拿不到上层常量时的唯一合法通路**。

成本：固化调用的 known 材料涨约 1515 字（基础 prompt 长度）。固化本身已带 12 条尾窗 + learned 全量，占比可接受；且清完存量（第 4 节）后 learned 那部分反而变小。

### 4. 存量清理（用户明示才动记忆资产）

删 `other.md` 10 条，两类：

- **2 条与基础 prompt 完全冗余**：语义/逐字检索区分（agent.py:37-39 + :74 已覆盖）、历史压缩后用 search_history（agent.py:72-74 已覆盖）
- **8 条过期临时状态**（价值已随时间归零，留着反而奖励「记住该忘的」）：PHP 函数封装下一步、气象预报窗口、Agent 规划需求未明确、RAG.md 缺内容、RAG.md 待补、笔记库 14 篇盘点、spawn 检索 RAG 的用户要求、OAuth 未找到

**不删** `constraints.md:8`（run_command 白名单确认）——它在 C1-9 实机验收里被测过，是活约束不是过期状态。

清理是**一次性手工动作，不建自动机制**：语义级「这条还有没有价值」的判断没有可靠的程序化判据，建了就是又一个死旋钮。

**清理时撞见的一处冲突（写 ADR 时未察觉，执行时发现）**：要删的冗余条目之一（语义/逐字检索区分）正是 `evals/memory_cases.py` 里 `o-two-search` 题的唯一答案来源。删条目 → 该题作废。裁定：**同步剔除该题**（13 题 → 12 题）。理由不是「迁就清理」，而是这道题本来就是废题——条目内容与 `DEFAULT_SYSTEM_PROMPT` 重复，而该 prompt **每轮注入**，无记忆组照样答得出，题目区分不出记忆有无（B 路消融的对照点失效）。已在 `memory_cases.py` 的剔除清单里新增第 ③ 类（与基础 prompt 冗余）对账，并注明文件头「24 条盘点」与 roadmap 8.7 记的 13/13 vs 4/13 都是**清理前**口径。

顺带把留下的 `run_turn` 条目也剥干净：原文带着「第 113 行、共 227 行已腐化为第 340 行、共 501 行」的对照叙述，正是本案闸门要拦的形态，留在库里等于文件不自洽。只保留稳定部分（文件路径），腐化实证数字已由本 ADR 与 `memory_cases.py` 文件头存档，不丢证据。

## 判定标准（验收用什么说话）

1. **易腐闸门生效**：喂一条含「第 113 行」的候选 → 不落盘，报告里出现该条原文；喂「架构分三层」「窗口约 7–10 天」→ 正常落盘（不误杀）
2. **对照物到位**：`_load_known` 返回值含基础 prompt 段；`base_prompt=""` 时与改动前逐字相同（默认行为不变）
3. **存量清理无副作用**：`read_learned` 解析剩余条目 0 坏行；消融场景集 `memory_cases.py` 的被剔除题不因清理而「意外变成可答题」
4. **三道门**：ruff / mypy / pytest 不回退（基线 518 passed, 2 skipped）
5. **重跑消融不崩**：`memory_cases.py` 剩余 12 题的指纹仍全部能在剩余 learned 条目里找到（清理没删掉被考的事实）。原 13 题里的 `o-two-search` 因其来源条目属冗余被删而同步剔除，见第 4 节

## 反方（预写）

1. **正则脆，表述千变万化拦不住**——成立。反驳：闸门是**第二道**不是唯一一道，第一道是提示词负面清单（带理由，能泛化）；正则只负责拦最常见的形态，拦不住的部分仍靠人审（记忆面板）。这与 `_SENSITIVE_PATTERNS` 的处境相同（换个格式的 key 也拦不住），但项目已接受这个权衡
2. **误杀真有用的条目**——真实风险，已用保守匹配收窄（只匹配「第 N 行」这类明确形态，不匹配裸数字）。且处置是「报告里显示原文」，误杀可当场发现并手工补回，不是静默丢失
3. **known 材料变长 → 固化 token 涨**——是，约 1515 字/次。反驳：固化是会话结束时的一次性调用（不是每轮），且这笔开销买的是「冗余条目从此查得出来」；不清理的话冗余条目会**每轮**注入，长期成本更高
4. **只治入口不治出口**——最有力的反方，成立。已入库的条目仍会腐化，本案没有过期机制。反驳：出口机制（tombstone / FR 四态）是 P2-1 另案，且 044 已把它定为写路径开闸的前置；本案先把入口收窄，**至少不让新的易腐事实进来**，存量靠人审（本次清理就是第一次人审）
5. **base_prompt 参数是不是加了个死旋钮**——不是。它有唯一合法消费者（`settle_session`），默认空值是为兼容既有调用点与测试，不是「留给未来某个可能的配置」；且下层拿不到上层常量时，参数传入是唯一不违反分层的通路
6. **清掉 8 条过期状态是不是过度清理**——用户明示。且判据是客观的：这 8 条描述的都是「某时刻的待办/缺口/查询结果」，其价值随该时刻过去而归零（气象窗口那条连日期都写死了 9/20 后再查）。留着的代价是每轮注入 token + 消融时反复人工剔除

## 不做（防范围蔓延）

- 不建过期/tombstone/FR 四态机制（P2-1 另案，044 已定为写路径前置）
- 不建 learned 自动去重工序（语义级重复判断无可靠程序化判据）
- 不改 learned 行格式、不加 schema 版本号
- 不重跑消融、不动已记录的通过率数字（本案是治理，不是重测）；`memory_cases.py` 只剔除因清理而失去答案来源的废题，其余题目与指纹一字不改
- 不给 `_harden` 加「易腐程度」分级旋钮（拦或不拦，二值）
- 不清 `constraints.md` / `decisions.md`（本次体检只照出 other.md 有问题）
