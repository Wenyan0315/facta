# cortex-from-scratch 架构与教学节奏评审

> 评审日期：2026-09-08
> 评审对象：`Wenyan0315/cortex-from-scratch`（main 分支快照，34 个文件 / 约 1100 行代码 + 750 行文档）
> 评审方式：全量通读源码与文档 + 离线实跑检索评估验证指标口径 + 量化启动期 embedding 开销
> 参照文档：`docs/architecture.md`（v0.13）、`docs/PROJECT_STORY.md`（v1.0）

## 0. 总体判断

**架构质量明显高于一般教学项目。** 三点站得住：

1. 分层干净，依赖方向基本单向：组装层 `__main__` → `core` → `llm / tools / memory / knowledge`
2. 接口与实现分离贯彻到底：`LLM` 与 `Embedder` 两处同构抽象，换实现上层不动
3. 决策记录写的是"为什么"而非"是什么"，且带日期、带翻车过程

`docs/architecture.md:144` 记录的 M5.5「放权后主循环 121→87 行，代码更少能力更强」是全项目最好的教学高光，可直接当教材使用。

**问题集中在两处：**

- **架构上**：状态管理是一条未收口的缝——底片持久化了，压缩缓存没有
- **教学上**：M6 膨胀失去节律 + 测试节奏完全缺位

以下按「架构」「教学节奏」两部分展开，每条都标注证据位置。

## 1. 架构评审

### 1.1 做得对的（建议保持，不要重构）

| 设计 | 位置 | 为什么好 |
|---|---|---|
| 两处同构抽象 | `llm.py` 的 `OpenAICompatibleLLM + PROVIDERS`；`knowledge_base.py` 的 `OpenAICompatibleEmbedder + EMBED_PROVIDERS` | 完全对称，加供应商 = 配置表加一行；不做"每家一个类" |
| `_EMBED_MODEL` 与 `_MODEL` 分离 | `knowledge_base.py:126` | 同一供应商的聊天/embedding 是两个独立开关，共用会互相覆盖。这是踩过坑才写得出的细节 |
| 阈值跟着实现走 | `knowledge_base.py:75` `default_min_score` 作为类属性 | 把量纲绑在实现上而不是散落调用方硬编码。很多人做 RAG 三年没想通这点 |
| 落盘策略归组装层 | `__main__.py:49-67`，`run_chat` 只进参出参不碰 IO | 控制反转用在了对的地方；换存储介质主循环零改动 |
| `execute` 错误也返回字符串 | `registry.py:63` | agent 容错的核心认知：让模型看见"哪里错了"才能自我纠正。不少框架都做错了 |
| 条件注册工具 | `builtin.py:254, 272` | 缺核心依赖就不上菜单，而不是上了菜单再运行时报错 |

### 1.2 需要修的问题（按优先级）

#### P0-1 压缩状态没有持久化：跨重启重摘要，长会话有炸上下文风险

**现象**
`summary` / `summarized_upto` 是 `run_chat` 的局部变量（`agent_loop.py:62-63`），而 `memory/store.py` 只序列化 `messages`。重启后 `summarized_upto` 归 1、`summary` 归 None。

**后果**

- 重启后第一次输入即触发 `maybe_compress`，此时 `fresh = messages[summarized_upto:start]` 是**整部历史**，被一次性塞进摘要器 → 会话越长这个 prompt 越大，迟早超上下文
- 精心设计的"滚动摘要"每次重启从零重来，成本 O(N) 反复付，且一次性摘要的保真度低于逐段滚动

**与既有设计的矛盾**
`agent_loop.py:28` 的人设声明"跨重启恢复 = 同一个持续会话"。事实是底片续上了、缓存没续上，人设与实现不一致。

**修法**
抽 `Session` / `ConversationState` 对象持有 `messages + summary + summarized_upto`，`store` 序列化整个对象，JSON 加 `version` 字段以便日后演进。这一步顺带解决状态无法单测的问题（局部变量测不到）。

#### P0-2 没有能产生 `tool_calls` 的假模型：工具链路只能靠真模型手工验收

**现象**
`MockLLM` / `EchoLLM` / `RepeatLLM` 三个假模型都只返回纯文本，无一能返回 `tool_calls`（`llm.py:60-110`）。

**后果**
工具循环、tool 消息与 `tool_calls` 的配对、窗口左边界的孤儿检测、`trim_incomplete_round` —— **全部无法离线验证**。这正是 `compressor.py:12` 自己写下的那句"mock 模型不校验，本地全绿、真模型间歇炸"的根因。

**修法**
加 `ScriptedLLM(script=[...])`：按脚本依次返回 tool_calls 或文本，约 25 行。之后所有不变量都能离线测试。**这是本次评审中投入产出比最高的一条。**

#### P1-1 `Message` 住在 `core/llm.py`，事实上成了跨层公共类型

`memory/store.py`、`memory/compressor.py`、`tools/builtin.py` 都 `from agent.core.llm import Message`——工具层为了一个数据类去依赖 core 的供应商实现。

**修法**：提到 `agent/types.py`（或 `core/types.py`），`llm.py` 只留接口与实现。这是全项目唯一一处分层瑕疵，越早改成本越低。

#### P1-2 `register_builtin` 的依赖注入即将失控

`register_builtin(registry, kb, llm, history)` 已 4 个参数、3 个闭包依赖，条件注册嵌套两层（`builtin.py:254, 272`）。M7 加向量库、M9 加 arXiv 就是 6 个参数。

**修法**：引入 `ToolContext` dataclass（`kb / llm / history / notes_dir / ...`）一次注入，条件注册可扁平化。

#### P1-3 路径硬编码在模块级，绑死工作目录

`NOTES_DIR = Path("data/notes")`（`builtin.py:65`）、`MEMORY_PATH = Path("data/memory/session.json")`（`__main__.py:23`）都是相对路径，换目录启动就找不到笔记、把记忆写到别处。

更值得注意的是**不对称**：`loader.load_notes(notes_dir=...)` 可传参，`builtin.py` 里同一份数据的路径却焊死。建议随 `ToolContext` 一起注入。

#### P2-1 启动时冗余 embedding，实测 4.4 倍

`__main__.py:43` 逐篇 `add_document`，而 `add_document` 每次都 `_rebuild()` 全量重算（`knowledge_base.py:189`）。当前语料实测：

```
最终块数 = 59
启动时实际 embedding 的块次数 = 261   → 4.4x 冗余
HTTP 请求次数 = 13（每篇一次全量重建）
```

增长是 O(N²)：100 篇笔记时约 50 倍。

`architecture.md:129` 已承认"O(N) 重算是教学版局限"，但这是**每次启动都在付真金白银和秒级延迟**，而修法只需加 `add_documents(list)` 批量接口 + 仅词袋需要 refit。**建议现在就修**，把"增量索引"留给 M7 的 Chroma。教学版可以简陋，但不该在启动路径上白烧 4 倍 token。

#### P2-2 `demo()` 让库文件反向依赖数据层

`knowledge_base.py:19` import `loader` 只为了第 214 行的 `demo()`。挪到 `scripts/` 或 `__main__` 子命令。

#### P2-3 检索评估的 P@k 口径是坏的

这条落在 M3.5「度量思维」的正题上，所以必须说。离线跑词袋基线的实测结果：

```
RAG 是什么           P@5=0.20  R@5=1.00  期望指纹数=1  命中块数=1
什么是检索增强生成     P@5=0.20  R@5=1.00  期望指纹数=1  命中块数=1
embedding 是干嘛的   P@5=0.20  R@5=1.00  期望指纹数=1  命中块数=1
PHP 是什么语言        P@5=0.40  R@5=1.00  期望指纹数=2  命中块数=2
```

**问题一：P@5 的理论上限就是 0.2。** 知识库里只有 1 个块含该指纹，分母却是 k=5。检索其实是完美的（该命中的都在 top-5），但报出来的平均 P@5≈0.22 会让人误判"检索很差"。这个指标现在实际在测量的是"每篇笔记被切成几块"。

**问题二：`recall_at_k` 分子分母口径不一致**（`retrieval_eval.py:37-41`）：分子是"命中的块数"，分母是"指纹条数"。当一条指纹因 `overlap=50` 落在两个相邻块的重叠区时，recall 会 > 1。当前语料笔记短未触发，但公式是错的。

**修法**

- 主指标换成 **Hit@k / MRR / R@k**
- recall 改为按指纹去重计数：`sum(1 for exp in expected if any(exp in c for c in retrieved[:k])) / len(expected)`
- 要保留 precision，就必须标注**全部**相关块；否则只报 P@1

#### P3 杂项

- **三个版本号在漂移**：`__main__.py:22` 的 `0.8.0` / `pyproject.toml` 的 `0.1.0` / 架构文档 `v0.13`
- **复制粘贴残渣**：`EchoLLM`（`llm.py:80`）、`RepeatLLM`（`llm.py:96`）的 docstring 是 `MockLLM` 原文照抄。项目自己在 `PROJECT_STORY.md:43` 把"复制粘贴残渣"列为踩过的坑
- **上下文预算策略不一致**：`read_history` 对 tool 结果截 300 字（`builtin.py:211`），`read_notes` 返回整篇不截断
- **工具结果全量打印到终端**（`agent_loop.py:97`）：读一篇 5KB 笔记会刷屏。M6.4 的"双通道分离"就是在还这笔债

## 2. 教学节奏评审

### 2.1 节奏上做得非常好的

1. **每个里程碑一个能力原子**，且都能用一句大白话讲清 —— `PROJECT_STORY.md` 的"装备清单"表就是这一点的证据（电话线 → 记事本 → 资料柜 → 考核表 → 双手 → 自主权）。
2. **先假后真、先手写后工业**：mock → DeepSeek，词袋 → BGE-M3。学员先看清原理，再看清工程，顺序是对的。
3. **M3.5 把度量插在 M4 之前**。绝大多数教程等项目做完才讲评测，这里提前了，而且是"改实现前先立基线"的正确姿势。
4. **踩坑沉淀成笔记，笔记又成为 RAG 语料**。`data/notes/三级信息政策.md` 就是 M5 提示词打架的复盘，而它同时是知识库的检索对象。学员的学习产物直接变成系统的燃料，这个自指闭环是本项目最妙的设计。
5. **活 spec 原则**（`architecture.md:12`）：方向锁定、细节临期定、事后回写决策。比"一开始画完整张大图"更接近真实工程。
6. **BGE 阈值校准法**（`architecture.md:137`）：先跑探针看分数分布，阈值卡在相关与垃圾之间的沟里。"数据定参，不拍脑袋"——这一课的价值远超它占用的时间。

### 2.2 节奏上的问题

#### 问题 1（主要）：M6 膨胀成一整段，学员会有进度停滞感

M6 现在是 **6.1 / 6.2 / 6.3a / 6.3b / 6.4** 五个子里程碑，但它们本质是同一个知识点（上下文管理）的反复打磨。从路线图看，M5.5 之后所有产出都是记忆层管道，而工具层（MCP、skills）、多 agent 这些"agent 的灵魂"反而停滞。

**M6.4 streaming 放在 M6 里是错位的**：它是增量协议 + UX 知识点，与记忆无关，只因"用户取消"这个副产品被吸进来。

**建议**：M6.3b 做完即封板；streaming 独立成里程碑，或直接并入工具层那一讲（`tool_calls` 分片重组本来就是工具层的事）。

#### 问题 2（最大）：测试节奏完全缺位

项目里没有 `tests/`，`pyproject.toml` 无 pytest 依赖。所有不变量——覆盖不变量、窗口左边界必须落在 user、孤儿 tool 消息、列表身份陷阱、查重闸门——全部靠"人工五轮验收"守，结论写进了 `architecture.md:152` 的散文里。

文档自己写下了那句话：「**不变量必须显式写下来才能被测到**」（`architecture.md:147`）。但它被写成了散文，不是断言。这些不变量现在依赖你记得住，而不是依赖 CI。

**建议**：在 M5.5 之后立刻插一节「**给 agent 写测试**」——`ScriptedLLM` + 5 个回归用例，每个用例对应一次真实的验收翻车。

教学价值我认为**高于 M6.3b**：它教的是"如何把踩过的坑变成再也不会踩的坑"，而「验收五轮 saga」正是这一课的完美素材——每轮失败都已有精确的复现路径，写成测试几乎免费。

#### 问题 3：M7.5 生产化加固排得太晚

M4 起就在打真 API，但超时/重试要等到 M7.5。`OpenAICompatibleLLM.generate`（`llm.py:171`）现在是裸调用：没 timeout、没重试。学员第一次遇到请求 hang 住或 429 时，手上什么都没有。

**建议**：把「超时 + 一次退避重试」下沉到 M4 收尾（20 行，`openai` 客户端原生支持）；熔断、降级链、请求度量留 M7.5。容错四件套拆成"入门两件 + 进阶两件"，更符合真实学习曲线。

#### 问题 4：悬挂项在磨损路线图可信度

- **MCP** 三次顺延，但仍画在架构图里（`architecture.md:73`、`145`）
- **LLM-as-judge** 从未获得编号，只写"M4后"，在文档中出现三处
- **`write_note` 语义查重**两次被提为"留给 M6 的 LLM-as-judge"，至今无主

活 spec 不等于允许无主项累积。**建议**：每个悬挂项二选一——给编号，或明确写"本阶段不做"。

#### 问题 5：文档到了拆分点

`architecture.md` 单文件塞了设计原则 + 全景图 + 状态表 + 路线图 + 20 条决策记录，单条决策已达 400 字（`:147` 那条摘要压缩记录）。带练项目里学员会反复回看，检索成本已经偏高。

**建议拆分**

| 文件 | 内容 |
|---|---|
| `architecture.md` | 只留设计原则 + 结构图 + 各层现状表 |
| `ROADMAP.md` | 里程碑与状态 |
| `decisions/ADR-0xx-*.md` | 一决策一文件，带日期编号 |

#### 问题 6：缺 README 和 `.env.example`

新人（或三个月后的自己）拿到仓库跑不起来：没有安装步骤、没有环境变量清单、不知道 `python -m agent mock` 可以离线玩。`.gitignore` 排除了 `.env` 却没提供模板。带练项目的第一印象就是 README，成本 20 分钟。

#### 问题 7：进阶段二之前缺一讲「工具风险分级与人在环审批」

`write_note` 的双重防线（路径穿越 + 查重闸门，`builtin.py:98-117`）是很好的种子。但阶段二的 coding agent 要开 shell、写任意文件，需要的是一个 **approval hook 抽象**（工具声明风险等级 → 高风险执行前回调确认），而不是每个工具各自硬编码栅栏。

现在"安全"那一讲排在 M9 前（`architecture.md:131`）。**建议提前并绑到工具层**：讲提示词注入与工具越权的最佳时机，就是给 agent 装 shell 之前。

## 4. 一句话总结

**架构地基是扎实的，主要缺的不是设计能力，而是"把已知的不变量固化成测试"这一环。**

教学节奏前半段（M0–M5.5）近乎教科书级；问题出在 M6 之后失去了"一个里程碑一个新能力"的节律，变成了同一层的反复打磨。
