整体评价

这个项目最难得的不是代码量，而是工程纪律：接口与实现分离、依赖注入单一真值源（assemble.py）、内核/外设分离（run_turn 零 input/print，全靠 on_text/on_event/should_cancel/on_confirm 四条缝）、每个里程碑都回写 ADR 决策记录。它已经把"玩具 agent"和"能上生产的 agent"之间的大部分地基打好了——网关四件套（记账/重试超时/缓存/熔断降级）、审计日志、权限分级、注入免疫条款，这些都是很多真实项目会漏掉的东西。

所以我下面的建议不是"补基础"，而是针对它从单轮工具循环走向真正 coding agent / 多 agent 时必然会撞上的几个结构性天花板。

一、主循环：从"固定保险丝"走向"可规划的循环"

现状 run_turn 是一个 for _round in range(5) 的 ReAct 循环，跑满就强制收尾。这个设计对当前场景够用，但有三个隐患：

轮数上限是硬编码的常量，不区分任务复杂度。 一个"查天气"和一个"跨文件重构"用同一个 5 轮保险丝，前者浪费、后者必然截断。建议把 _MAX_TOOL_ROUNDS 变成预算对象：按任务类型/用户设定注入，并且和 token 预算、成本预算统一成一个 Budget，在循环里同时消耗。你的网关已经有 UsageLedger 记账，把"预算"和"账本"对接起来，就能做到"接近预算时提前收尾并告诉用户为什么"，而不是默默熔断。

没有显式的规划阶段。 现在是纯反应式（模型每轮临时决定下一步）。对 coding agent 来说，建议引入一个轻量的 plan-then-act：复杂任务先让模型产出一个 todo/plan（你已经有 TodoStore 和 todo 工具，天然可复用为"执行计划"的载体），再进入循环，每完成一步回写 plan 状态。这也正好呼应你文档里"Human on the Loop——让人定义、掌舵、评判"的原则：plan 是给人看的掌舵点。

工具是串行的。 for tc in reply.tool_calls 顺序执行。模型一次点多个菜时（比如同时读 3 个文件），完全可以并行。建议对 is_readonly=True 的只读工具走线程池并行，写类工具保持串行。这是 coding agent 提速最直接的一招。

二、上下文管理：滚动摘要之外的两个缺口

compressor.py 的滚动摘要 + 原文窗口 + "覆盖不变量"（每条消息要么被摘要覆盖要么原文在 payload）设计得很扎实，孤儿 tool 消息的防御也到位。但有两个更进阶的问题：

摘要压缩是"位置驱动"而非"信息密度驱动"。 现在按 len(fresh) >= 6 触发，窗口固定 KEEP_LAST=6。对 coding agent，一段关键的工具输出（比如一个报错栈、一份 schema）可能比 10 轮闲聊都重要，但它会一样被摘要稀释。建议给消息加保留权重/锚点：被模型或规则标记为"关键事实"的消息，即使滑出窗口也原文保留（或进一个独立的"事实区"常驻 payload）。

工具输出没有独立的裁剪策略。 一个 run_command 或 search_code 可能返回 6000 字，直接进 payload 会挤占预算。建议在 Message 落底片前对超长 tool result 做结构化裁剪（保留头尾 + 中间省略标记，或抽取关键行），且裁剪逻辑可被工具声明（只读检索类可激进裁剪，diff 类必须保真）。

三、记忆固化：把"审查员"升级成真正的质量闸门

consolidate.py 的四段管线（萃取→审查→硬校验→落盘）思路非常好，尤其是"档案员不是评论员"的纪律和"用户级信息不进项目级仓库"的红线，这是很多 agent 记忆系统会踩的坑。两点建议：

审查员目前是"第二次 LLM 调用对照原文"，你自己也注记了"幻觉率实测 >0 才升级跨供应商裁判"。 建议提前一步：让审查员输出结构化的判定理由（每条 entry 标注"依据原文哪一句"），这样既能提高审查质量，也让 data/learned/ 的每条记忆可溯源。溯源性对记忆系统的长期可信度至关重要。

缺少记忆的"衰减/冲突消解"机制。 现在是 append 到 {类别}.md，批内去重、批间靠提示词比对。随着时间推移必然出现过期记忆（决定被推翻、约束已失效）和冲突记忆。建议给每条 entry 加元数据（来源会话、时间戳、置信度），并设计一个定期的"记忆体检"任务做冲突检测和过期清理——这比无脑 append 更可持续。

四、安全模型：确认机制已经很好，补两处

S3/S4 的权限分级（L0/L1/L2）、注入界碑、SSRF 栅栏、run_command 白名单免确认（无 shell 元字符才放行）都设计得很专业。补充：

注入免疫目前是"提示词层防御"（SYSTEM_PROMPT 里的免疫条款）。 这对弱攻击有效，对强攻击不够。建议在数据层再加一道：所有外部内容（web/搜索结果/文件）回填为 tool message 时，用固定的、模型难以混淆的定界符包裹并显式标注"以下为不可信数据"，且对高危工具（run_command、write_file）在确认弹窗里向用户展示触发它的原始上下文，让人成为最后一道判断。你的 on_confirm 缝已经具备这个能力，只是弹窗内容要带上"为什么模型想做这件事"。

白名单是字符串前缀匹配，存在绕过面。 needs_confirm 已经防了 shell 元字符和路径前缀，很谨慎。但像 find ... -exec、grep 配合特殊 flag 这类"只读命令名 + 危险参数"仍可能漏。建议白名单从"命令名"升级到"命令名 + 参数模式"的联合校验，或干脆对高危参数（-exec/-delete/--force）做黑名单拦截。

五、为多 agent（S6）提前铺路

你路线图里 S6 是多 agent 协作，判据写的"噪声隔离"很准。现在 search_and_summarize 已经是 sub-agent 原型（工具内部调 LLM）。建议：

现在就把"agent"抽象成一等公民，而不是等到 S6。具体说，把 run_turn 里"一个带工具的 LLM 循环"提炼成一个可复用的 Agent 对象（有自己的 system prompt、工具子集、预算、记忆），主 agent 通过一个 spawn_subagent(task, tools, budget) 工具来派生子 agent，子 agent 只回传结论而非全过程（这正是噪声隔离）。这样 S6 就是水到渠成，而不是大重构。你现在的 assemble.py 依赖注入结构已经很适合做这件事。

六、可观测性与评测：把已有的雏形连成闭环

evals/ 有检索评估 + LLM-as-judge，telemetry 有账本，audit 有日志——三块都在，但是分散的。建议做一个统一的 run trace：把一次 run_turn 的每轮决策、工具调用、token 消耗、审计事件串成一条可回放的轨迹（你的 Web Run Store 已经有 append-only 带 seq 的事件流，天然是 trace 的载体）。有了完整 trace，评测就能从"最终答案质量"扩展到"过程质量"（工具选得对不对、有没有绕路、有没有幻觉调用），这对迭代 agent 行为的价值远大于只看最终答案。

从工程师视角看，这个项目的设计品味远超它的工程基础设施——架构分层、决策记录、测试契约都很成熟，但支撑它"长成生产级 coding agent"的那些脏活（日志、配置、静态检查、并发、故障处理）明显滞后。下面按"会不会真咬人"排序，都带代码位置。

一、会直接咬人的隐患（correctness / robustness）

run_turn 返回 None 有二义性，调用方无法区分"被取消"和"模型全挂"。
loop.py 里取消和 LLMUnavailableError 两条路径都 return None。虽然错误走了 on_event("error")、取消不发事件，但函数签名层面调用方拿到 None 是懵的。Web 的 _run_worker 要靠"有没有收到 error 事件"来反推状态，这是隐式契约,很容易在新增终态时漏判。建议返回一个带 reason 的结果对象（TurnResult(status=cancelled|error|ok, message=...)），把"为什么没产出"变成显式类型。

多线程 Web 模型 vs 明确声明"不需要锁"的共享状态。
server/app.py 每个 run 起一个 daemon Thread，但：
audit.py 白纸黑字写"单进程 append 模式下不需要锁；留位多线程高频写时补"——Web 已经是多线程了，多个 run 并发 append 同一天的 jsonl，靠的只是 POSIX O_APPEND 对小写的隐式原子性，代码既没依赖也没说明这个保证。
telemetry.py 的 UsageLedger 是全局单例，+= 非原子，跨线程记账会丢数。
ToolRegistry 被所有 run 线程共享，虽然目前只读，但 MCP 的 unregister（摘死菜）是写操作，并发下有竞态。

单用户低并发不会炸，但文档标榜"企业级视角贯穿每个里程碑"——这就是那个视角该覆盖却没覆盖的地方。

降级链兜底到 mock 是"静默污染"的生产版。
get_llm 默认 with_mock_fallback=True，真模型全挂时自动切 MockLLM 继续对话。评测模式关掉了这个（很对），但生产用户会拿到 [mock] 本轮共收到 N 条历史… 这种回复而可能没意识到模型挂了。虽然 FallbackLLM 会打印声明，但混在 41 处 print 里极易被忽略。降级到 mock 应该是显式的、阻断性的用户可见状态，而不是悄悄顶替。

LLM 接入层缺基本参数透传和流中断保护。
OpenAICompatibleLLM.generate/generate_stream 完全没有 max_tokens / temperature / top_p 的口子——生产里你无法控制输出长度、无法调采样。更要命的是流式：只有"第一块之前"可重试，第一块吐出去后中途断线直接抛异常，用户看到半句话就没了。gateway 自己也承认这个语义。对 coding agent 的长输出这是高频故障点。

二、工程基础设施缺口（可观测性 / CI / 配置）

零结构化日志，41 处 print 散在库代码里。
logging 模块用了 0 次。compressor.py、gateway.py、assemble.py、loop.py 这些内核库直接 print 到 stdout。这和它自己精心设计的 on_text/on_event I/O 缝自相矛盾——一边主张"内核不知道自己在 CLI 还是 Web 里跑"，一边内核到处 print。后果：Web 模式下这些输出污染、无法分级、无法关闭、无法重定向到日志系统。这是最该先补的一刀:内核全部改 logging + 可注入 handler,把 print 收进 CLI 壳。

CI 只跑 pytest，类型标注是"纸面安全"。
.github/workflows/ci.yml 只有 pytest。项目写满了 type hints（from __future__ import annotations、完整签名），但没有 mypy、没有 ruff/lint、没有 coverage gate，pyproject 里也没声明这些工具。写了类型却不在 CI 校验，等于类型系统的好处一分没拿到。对一个以"工程纪律"为卖点的项目，这是明显的反差。

配置与路径管理脆弱，且违反自己定的规则。
paths.py 自己承认"仍是相对路径，依赖从仓库根启动"是已知边界。NOTES_DIR/LEARNED_DIR 用相对路径，但 WORKSPACE_ROOT 用 __file__ 锚定——同一个文件里两套路径锚定方式，换 CWD 启动时数据路径和围栏根会指向不一致的地方。
更打脸的是：paths.py 立的规矩是"跨模块共享路径收口到这里"，但 MEMORY_PATH / VECTOR_DB_DIR / TODOS_PATH / AUDIT_DIR 全散在 assemble.py 里各自 Path("data/..."),没进 paths.py。它治理了 notes 路径的漂移,却留了四个新的漂移点。
没有统一的 settings/config 层（pydantic-settings 之类），环境变量命名约定 {PREFIX}_API_KEY 靠口头约定散落各处。

三、架构一致性 debt（自己标注的"已知边界"累积）

缓存与状态的浅拷贝共享引用。 gateway 精确缓存是进程内 LRU 不落盘（重启语义缓存的 embedding 钱白花），且 replace() 是浅拷贝,tool_calls 列表仍与缓存本体共享引用——代码注释自己写"若有人改动返回消息的 tool_calls,隔离会被击穿(已知边界)"。靠约定不靠机制的不可变性,迟早被破。

手写 MCP 客户端的边界会变成真实故障。 mcp_client.py 承认:per-request timeout 不是总超时(服务器持续吐无关消息可无限等)、stderr DEVNULL 丢调试证据、协议版本硬编码 2024-11-05、后台读线程的 queue 无上限(恶意/故障 server 无限输出可撑爆内存)。教学价值很高,但 MCP 是 coding agent 的核心积木,这些边界排期转正时会集中爆发。

依赖治理松。 openai>=1.0、chromadb>=1.5 这种宽上界约束,没有 lockfile,跨大版本 breaking change 无防护。

测试扎实但缺三类。 4002 行测试 / 30 文件、ScriptedLLM 的设计都很优秀。但缺:①并发/竞态测试(正好对应隐患 2);②熔断降级链在真实故障序列下的集成测试;③长会话压缩的保真度回归(防摘要漂移——compressor 的"覆盖不变量"目前靠单测,没有端到端的"关键事实在 N 轮压缩后还在不在"的回归)。真模型验收全靠 PYTEST_LIVE_NETWORK=1 手动跑,CI 里从不验证真实链路。

从产品经理视角看，这个项目最大的问题不在功能，而在定位的摇摆——它在"作者自用的学习项目"和"想做成的通用产品"之间反复横跳，导致功能取舍没有统一标尺。下面按产品逻辑排序。

一、定位："三场景并列 + 数据驱动排序"是伪命题

product.md 写的是"通用个人 agent，知识/助理/工程三块并列不分主次，优先级由真实使用数据动态排序"。听起来很务实，但作为 PM 我会直接挑战两点：

三场景并列 = 没有定位。 对单用户项目，资源本就有限，三个场景平摊的结果是每个都做到 60 分。Cursor 赢在"围着代码转"的取舍，你的文档也承认这点，但结论却是"我们不平摊"——这在产品上是自相矛盾的。应该先押一个场景做到 90 分,而不是三个 60 分。从代码完成度看,知识伴侣(RAG+记忆+固化)明显最成熟,那就该把它定为楔子。

"数据驱动排序"的数据根本不够。 使用数据台账里只有寥寥几条(2026-09-15 五段对话),这种样本量支撑不了优先级决策——这是用"数据驱动"的话术包装"拍脑袋"。真正该做的是先明确一个目标用户画像(哪怕是作者自己),用画像反推优先级,而不是等数据攒够。

二、核心体验:信任与可解释性被当成了技术细节

文档自己立的产品哲学是"人负责定义、掌舵、评判",但 UI 上用户根本没法评判:

RAG 回答没有引用溯源。 SYSTEM_PROMPT 里郑重承诺"基于笔记回答、答不了诚实说、通用知识要标注",但 Web/CLI 上回答就是一段纯文本,没有 citation、没有"基于哪条笔记"。用户无法验证 agent 到底是查了笔记还是在编——这直接架空了它自己承诺的诚实。对个人 agent,可信度就是产品命脉。

工具调用只展示 raw 参数和结果字符串。 app.js 的 addToolCard 显示的是 name(args) + result。用户看到的是"调了 search_notes({query:...})",而不是"为了回答你,我查了 X 笔记、执行了 Y"。过程可解释性是 agent 产品区别于黑箱模型的核心体验,现在完全没做。

三、留存 loop:全是被动响应,没有主动价值

用户不来,产品就不产生任何价值。 现在所有能力(问答、待办、检索)都是被动等用户发起。个人 agent 的产品生命线是"用户为什么每天回来",而唯一能主动触达的 M9(论文推送/cron 任务)被排到了"支线·可跳"。这是把留存引擎当成了可有可无的支线。

记忆固化(data/learned)是差异化资产,却被埋没。 跨会话记忆是个人 agent 最值钱的护城河,但用户看不见、感知不到它在起作用——没有"你的 agent 记住了什么"的界面,没有记忆生效时的提示。花了大力气做的四段固化管线,产品价值是 0 可见度。

用户对"自己的第二大脑"没有掌控感。 记忆和笔记是核心资产,但没有:记忆的查看/编辑/删除 UI(被记了什么完全是黑箱)、导出/备份、跨设备同步。用户无法掌控自己数据的产品,信任建立不起来。

四、功能取舍:该重投的没投,该缓的排太后

任务视图是半成品,但它是主战场。 长任务(Run)的后台执行、状态跟踪、回来看结果——这正是"执行成本归零后,注意力是稀缺资源"的核心场景,也是个人 agent 区别于聊天机器人的关键。现在 tasks.html 只有 60 行最小版,还带着"任务视图偶发不切换"的已知 bug。该重投的地方写着"按双视图预留未实现"。

多渠道(S8)排到最后,和使用频次形成死循环。 个人 agent 要融入"完整工作与生活",用户不会专门开电脑进 Web 页——得在 IM/手机上随手可用。但 S8 排在阶段二后段,意味着很长一段时间产品只能"坐在电脑前用",严重压制使用频次;而使用频次又是它优先级排序的依据——低频次→没数据→无法排序→继续低频。这个循环必须靠提前做多渠道来打破。

确认机制会引发确认疲劳。 run_command 非白名单全弹窗。文档自己提到"防狼来了效应",但产品上没有分级信任、没有"本会话不再问"、没有批量确认。长任务里频繁弹窗会把"Human on the Loop"变成"Human 点批准点到崩溃"。

首次体验(onboarding)缺失。 新用户打开 Web 面对空对话框,emptyHint 只有一句话,没有能力发现、没有示例 prompt、没有"我能帮你做什么"。SYSTEM_PROMPT 里塞了一大段自我画像,界面上却没有对应的帮助入口——agent 的能力和用户能感知到的能力之间有巨大鸿沟。

五、成功度量:只有模型指标,没有产品指标

evals 度量的是模型,不是产品。 检索 P/R、LLM-judge 回答质量都是技术指标。产品侧完全没定义北极星:任务完成率?用户纠正率(agent 做错被用户改的比例)?记忆命中带来的重复提问下降?会话留存?product.md 的"一句话验收"全是定性的,没有可量化的成功标准,就无法判断迭代到底有没有让产品变好。

---

如果我是这个产品的 PM,只做三件事:
砍定位——明确押"知识伴侣"单场景,把 RAG 引用溯源(3)做出来,让"可信问答"成为能对外讲的价值主张;
让记忆可见可控——加一个"记忆面板"(6+7),用户能看到/编辑 agent 记住的东西,把已有的固化管线变成可感知的差异化体验;
定义 3 个产品指标(12)——哪怕只有作者一个用户,也用"任务完成率/纠正率/记忆命中率"驱动迭代,取代样本不足的"使用数据排序"。

需要的话,我可以把这些整理成一份带优先级(P0/P1/P2)和验收标准的产品改进 backlog,或者针对某一条(比如"RAG 引用溯源"或"记忆面板")画出具体的交互方案。
