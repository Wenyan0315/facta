整体评价

这个项目最难得的不是代码量，而是工程纪律：接口与实现分离、依赖注入单一真值源（assemble.py）、内核/外设分离（run_turn 零 input/print，全靠 on_text/on_event/should_cancel/on_confirm 四条缝）、每个里程碑都回写 ADR 决策记录。它已经把"玩具 agent"和"能上生产的 agent"之间的大部分地基打好了——网关四件套（记账/重试超时/缓存/熔断降级）、审计日志、权限分级、注入免疫条款，这些都是很多真实项目会漏掉的东西。

所以我下面的建议不是"补基础"，而是针对它从单轮工具循环走向真正 coding agent / 多 agent 时必然会撞上的几个结构性天花板。

一、主循环：从"固定保险丝"走向"可规划的循环"

现状 run_turn 是一个 for _round in range(5) 的 ReAct 循环，跑满就强制收尾。这个设计对当前场景够用，但有三个隐患：

轮数上限是硬编码的常量，不区分任务复杂度。 一个"查天气"和一个"跨文件重构"用同一个 5 轮保险丝，前者浪费、后者必然截断。建议把 _MAX_TOOL_ROUNDS 变成预算对象：按任务类型/用户设定注入，并且和 token 预算、成本预算统一成一个 Budget，在循环里同时消耗。你的网关已经有 UsageLedger 记账，把"预算"和"账本"对接起来，就能做到"接近预算时提前收尾并告诉用户为什么"，而不是默默熔断。

没有显式的规划阶段。 现在是纯反应式（模型每轮临时决定下一步）。对 coding agent 来说，建议引入一个轻量的 plan-then-act：复杂任务先让模型产出一个 todo/plan（你已经有 TodoStore 和 todo 工具，天然可复用为"执行计划"的载体），再进入循环，每完成一步回写 plan 状态。这也正好呼应你文档里"Human on the Loop——让人定义、掌舵、评判"的原则：plan 是给人看的掌舵点。

工具是串行的。 for tc in reply.tool_calls 顺序执行。模型一次点多个菜时（比如同时读 3 个文件），完全可以并行。建议对 is_readonly=True 的只读工具走线程池并行，写类工具保持串行。这是 coding agent 提速最直接的一招。

二、上下文管理：滚动摘要之外的两个缺口

compressor.py 的滚动摘要 + 原文窗口 + "覆盖不变量"（每条消息要么被摘要覆盖要么原文在 payload）设计得很扎实，孤儿 tool 消息的防御也到位。但有两个更进阶的问题：

摘要压缩是"位置驱动"而非"信息密度驱动"。 现在按 len(fresh) >= 6 触发，窗口固定 KEEP_LAST=6。对 coding agent，一段关键的工具输出（比如一个报错栈、一份 schema）可能比 10 轮闲聊都重要，但它会一样被摘要稀释。建议给消息加保留权重/锚点：被模型或规则标记为"关键事实"的消息，即使滑出窗口也原文保留（或进一个独立的"事实区"常驻 payload）。

工具输出没有独立的裁剪策略。 一个 run_command 或 search_code 可能返回 6000 字，直接进 payload 会挤占预算。建议在 Message 落底片前对超长 tool result 做结构化裁剪（保留头尾 + 中间省略标记，或抽取关键行），且裁剪逻辑可被工具声明（只读检索类可激进裁剪，diff 类必须保真）。

三、记忆固化：把"审查员"升级成真正的质量闸门

consolidate.py 的四段管线（萃取→审查→硬校验→落盘）思路非常好，尤其是"档案员不是评论员"的纪律和"用户级信息不进项目级仓库"的红线，这是很多 agent 记忆系统会踩的坑。两点建议：

审查员目前是"第二次 LLM 调用对照原文"，你自己也注记了"幻觉率实测 >0 才升级跨供应商裁判"。 建议提前一步：让审查员输出结构化的判定理由（每条 entry 标注"依据原文哪一句"），这样既能提高审查质量，也让 data/learned/ 的每条记忆可溯源。溯源性对记忆系统的长期可信度至关重要。

缺少记忆的"衰减/冲突消解"机制。 现在是 append 到 {类别}.md，批内去重、批间靠提示词比对。随着时间推移必然出现过期记忆（决定被推翻、约束已失效）和冲突记忆。建议给每条 entry 加元数据（来源会话、时间戳、置信度），并设计一个定期的"记忆体检"任务做冲突检测和过期清理——这比无脑 append 更可持续。

四、安全模型：确认机制已经很好，补两处

S3/S4 的权限分级（L0/L1/L2）、注入界碑、SSRF 栅栏、run_command 白名单免确认（无 shell 元字符才放行）都设计得很专业。补充：

注入免疫目前是"提示词层防御"（SYSTEM_PROMPT 里的免疫条款）。 这对弱攻击有效，对强攻击不够。建议在数据层再加一道：所有外部内容（web/搜索结果/文件）回填为 tool message 时，用固定的、模型难以混淆的定界符包裹并显式标注"以下为不可信数据"，且对高危工具（run_command、write_file）在确认弹窗里向用户展示触发它的原始上下文，让人成为最后一道判断。你的 on_confirm 缝已经具备这个能力，只是弹窗内容要带上"为什么模型想做这件事"。

白名单是字符串前缀匹配，存在绕过面。 needs_confirm 已经防了 shell 元字符和路径前缀，很谨慎。但像 find ... -exec、grep 配合特殊 flag 这类"只读命令名 + 危险参数"仍可能漏。建议白名单从"命令名"升级到"命令名 + 参数模式"的联合校验，或干脆对高危参数（-exec/-delete/--force）做黑名单拦截。

五、为多 agent（S6）提前铺路

你路线图里 S6 是多 agent 协作，判据写的"噪声隔离"很准。现在 search_and_summarize 已经是 sub-agent 原型（工具内部调 LLM）。建议：

现在就把"agent"抽象成一等公民，而不是等到 S6。具体说，把 run_turn 里"一个带工具的 LLM 循环"提炼成一个可复用的 Agent 对象（有自己的 system prompt、工具子集、预算、记忆），主 agent 通过一个 spawn_subagent(task, tools, budget) 工具来派生子 agent，子 agent 只回传结论而非全过程（这正是噪声隔离）。这样 S6 就是水到渠成，而不是大重构。你现在的 assemble.py 依赖注入结构已经很适合做这件事。

六、可观测性与评测：把已有的雏形连成闭环

evals/ 有检索评估 + LLM-as-judge，telemetry 有账本，audit 有日志——三块都在，但是分散的。建议做一个统一的 run trace：把一次 run_turn 的每轮决策、工具调用、token 消耗、审计事件串成一条可回放的轨迹（你的 Web Run Store 已经有 append-only 带 seq 的事件流，天然是 trace 的载体）。有了完整 trace，评测就能从"最终答案质量"扩展到"过程质量"（工具选得对不对、有没有绕路、有没有幻觉调用），这对迭代 agent 行为的价值远大于只看最终答案。
