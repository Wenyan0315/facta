# cortex-from-scratch 带练项目评审：架构 + 教学节奏

> 评审对象：`cortex-from-scratch-main.zip`（GitHub main 分支快照）
> 评审范围：34 个文件 / 1244 行 src / 142 行 evals / 2 份文档 / 13 篇语料
> 评审方式：全量读码 + 关键路径实测复现
> 日期：2026-09-08

---

## 一、总体结论

架构**骨架是对的**，教学节奏**前半段（M0–M5.5）质量很高**。问题集中在三处：

| # | 结论 | 性质 |
|---|---|---|
| 1 | 架构上有 4 个已经在漏的洞，其中 2 个已实测复现 | 需修 |
| 2 | 教学节奏在 M6 塌陷：一个"记忆"里程碑拆成 5 个子节点，占决策记录篇幅约 40%，而这恰是最不可迁移的部分 | 需重排 |
| 3 | 测试从头到尾缺位：1244 行 src、0 行单测，M0–M9 无任何测试节点 | 需补节点 |

---

## 二、做得对的部分（不展开）

- `LLM` 接口 + mock 先行 —— 链路与 API key/成本解耦，全项目最值钱的一步
- 词袋 → BGE 的"从简到真"，配合 **M3.5 先建度量再升级** —— 顺序罕见地正确，绝大多数教程做不到
- M5.5 把 `kb.search` 包成工具后主循环反而变短 —— "放权换来复杂度塌缩"是最好的教学时刻
- `ToolRegistry.execute` 错误返回字符串而非抛异常，让模型自我纠正 —— 判断成熟
- 决策记录里实证驱动的痕迹（M6.2 翻车 → 逼出 M6.3 `read_history`）—— 真实工程质感

## 三、架构问题（按严重度排序）

### 问题 1【最严重】压缩状态没落盘，滚动摘要退化成全量重摘要

**现象**
`summary` / `summarized_upto` 是 `run_chat` 的局部变量（`agent_loop.py:62-63`），每次启动重置为 `None` / `1`；`memory/store.py` 只序列化 `messages`。

**实测**（41 条历史，FakeLLM 计数）

| 场景 | 摘要调用次数 | 单次并入消息数 |
|---|---|---|
| 进程不重启，连续对话 | 1 | 36 条 |
| **重启后第一轮** | **1** | **42 条（从头再来）** |

**根因与代价**
M6.2 精心设计的"早触发、宁可每次压小块、拒绝快满才压"，一遇重启就退化成它极力避免的**悬崖式大压缩**。档案涨到几百条时，启动首轮即一次巨型 LLM 调用。

附带两个后果：
- 摘要内容每次重启都不同 → "暗号跨压缩存活"的验收结论**不可复现**
- M6.1 的持久化与 M6.2 的压缩**没有组合起来**（各自正确，合起来失效）

**修法**
`session.json` 升级为带版本号的结构：

```json
{
  "version": 1,
  "messages": [...],
  "memory": { "summary": "...", "summarized_upto": 37 }
}
```

顺带白送一节"存储格式演进 / schema 版本化"的课。

---

### 问题 2 任何 API 异常都会丢掉整段历史

**现象**
`run_chat` 只捕获 `KeyboardInterrupt / EOFError`。`llm.generate` 抛出的 `APIError`、超时、连接重置会一路穿到 `__main__.main()`，**直接跳过 `save_messages`**（`__main__.py:64-67` 之间无 `try/finally`）。

而 `OpenAICompatibleLLM.generate` 与 `OpenAICompatibleEmbedder.embed` **都没有 timeout、没有重试**。

**代价**
从 M4 接入真模型那天起，一次网络抖动 = 本次会话新增的全部对话蒸发。

这同时是"M7.5 排太晚"的直接证据（见节奏问题 3）。

**修法**
`main()` 用 `try/finally` 包住 `run_chat`（一行缩进），或改成每轮落盘。

---

### 问题 3 evals 与线上共用**可变**语料 → 指标不可复现

**现象**
`architecture.md` 第 98 行把"evals 与线上共用同一份语料"列为优点。但这份语料是 agent 用 `write_note` **能自己改**的。

**实测**（词袋离线路径，对比 3 篇 agent 自写笔记入库前后）

| 指标 | 仅原始 10 篇 | 含 3 篇自写笔记 |
|---|---|---|
| 文本块数 | 11 | **59** |
| "中国的首都是哪"最高分 | 0.297 | 0.260 |
| "怎么做饭好吃"最高分 | 0.224 | 0.152 |
| "AI研发的学习路径是什么"最高分 | 0.300 | **0.224** |

闸门尚未击穿，但**基线已经在漂**。

**更深的问题**
3 篇自写笔记占语料 **92% 体积、81% 文本块**。一个号称"个人学习笔记"的知识库，绝大部分是关于它自己的治理文档，检索时会稀释真正的学习内容。

**最尖锐的一点**
`CASES` 里"AI研发的学习路径是什么"期望"检索不到"。哪天 agent 自己写了一篇学习路径笔记，这条用例就 FAIL —— 不是回归，是语料变了。

> 度量思维那一课，被自己的自我进化闭环拆了台。

**修法**
- 冻结 `evals/fixtures/notes/`（同一个 loader，不同目录），线上语料随便长
- `CASES` 硬编码在 `dataset.py` 里，违反项目自己在 Q2 立的"数据与代码分离"——架构图第 82 行画的 `evals/data/` 其实不存在，按图落地即可

---

### 问题 4 声称"完全对称"的两层，物理上不对称

**现象**
决策记录写"`OpenAICompatibleEmbedder` 与 llm.py 完全对称"。逻辑上是，**文件布局上不是**：

| 层 | 位置 | 行数 | 混合职责数 |
|---|---|---|---|
| LLM | 独占 `core/llm.py` | 227 | 1 |
| Embedder | 塞在 `knowledge/knowledge_base.py` | 236 | **5** |

`knowledge_base.py` 混了：分词/切块工具、`Embedder` 抽象、供应商配置表、`KnowledgeBase`、`demo()`。

**为什么这在教学项目里更严重**
学习者打开目录看到的结构，和"分层解耦"的口号不一致。**教学项目里，目录结构本身就是教材。**

**修法**
拆成 `knowledge/embedder.py` + `knowledge/knowledge_base.py`（可再拆 `chunking.py`）。

**顺带一处会误导人的陈旧数字**
`knowledge_base.py:73` 注释写"BGE 的 0.45"，实际配置表与决策记录都是 **0.55**。

### 其他（低优先，一并列出）

| 项 | 说明 |
|---|---|
| `tools/builtin.py` 327 行、6 层嵌套闭包 | 工具函数无法独立 import/测试；schema 与函数隔 60 行；`register_builtin(registry, kb, llm, history)` 每加依赖多一个位置参数，接 MCP 时必炸。建议按工具组拆模块，各暴露 `make_tools(deps)`，`deps` 用小 dataclass 装 |

| 缺 README / `.env.example` / ruff·black 配置 / pyproject dev 依赖 | 一个要给别人带练的项目，缺入口 |
| 三个版本号互不相干 | `pyproject 0.1.0` / `__main__ VERSION 0.8.0` / `architecture.md v0.13` |

## 四、教学节奏

### 前半段（M0–M5.5）：优秀，不用改

```
mock 先行 → 会话记忆 → 词袋 RAG → 先度量 → 换真模型+真向量 → 工具 → 放权
```

每一步的"下一步动机"都由上一步的痛点自然长出来，这是最难做到的。M3.5 把评估放在 M4 升级**之前**，尤其难得。

---

### 节奏问题 1：M6 严重超重，且是最不可迁移的部分

**现象**
M6.1 → 6.2 → 6.3a → 6.3b → 6.4，五个子节点全在"会话记忆"上。决策记录里 M6 相关条目占全部篇幅约 40%，单条 bullet 超过 600 字。

**对比**
被文档称为"全项目灵魂"的 M5 工具调用，只有 1 + 1（M5.5）个节点。

**为什么代价大**
真实项目里，跨会话记忆的存储、上下文压缩、prompt caching 基本由框架或供应商侧接管，且能力在快速变化。学习者在这里花的时间与收获不成正比。

**建议**
把 **M6.3b 多会话管理**和 **M6.4 streaming** 从 M6 摘出去：
- 多会话本质是"会话隔离 + 状态管理"，与记忆压缩不是一件事
- streaming 是交互层能力，与记忆完全无关，挂在 M6 下纯属就近堆放

M6 收在 **6.1 持久化 + 6.2 压缩 + 6.3 温层检索**，三节收官，干净。

---

### 节奏问题 2【最大缺口】测试从头缺位

**现状**
- `tests/` 不存在，pytest 不在依赖里
- M0–M9 + 阶段二，**无任何节点涉及测试**
- M6.2 的死区 bug，靠人肉"验收五轮 saga"逐层剥出来

**为什么现在就该补**
`window_start`、`build_payload`、`trim_incomplete_round` 都是**纯函数**，教科书级的第一批单测对象。"每条消息必须可见"这个覆盖不变量，写成 property test 三行搞定，当场就能拦住暗号落进死区。

> 决策记录自己写了："不变量必须显式写下来才能被测到"——那就写成断言，不是写成注释。

一个号称终点是企业级的项目，1244 行零单测说不过去。

**建议**
插入 **M2.5 或 M3.6：第一批单测**，就在 evals 旁边落地。evals 已是度量思维的雏形，把"离线指标"与"单元断言"两种度量对照着讲，是个很好的教学点。

---

### 节奏问题 3：M7.5 生产化加固排太晚

**现象**
从 M4 起就在打真 API，但重试/超时/熔断排在 M7 **之后**。架构问题 2 已证明代价：一次网络抖动就丢历史。

**建议**
把"**超时 + 一次重试**"这个最小组合下沉到 **M4 收尾**（就两行 kwargs），熔断/降级链/度量留在 M7.5。

这样既不破坏 M4 的教学焦点，又让"真 API 就是会失败"在第一次接触真 API 时就被教到。

---

### 节奏问题 4：M8 / M9 与终点目标脱节

**现象**
阶段二目标是"个人 coding agent"。coding agent 需要：文件读写与多文件编辑、shell 工具、diff 应用、子 agent 编排、streaming、MCP。

而 M8 是知识图谱、M9 是论文推送（cron + arXiv）——两个都是**学习助手**方向的支线，对 coding agent 几乎零复用。

同时 **MCP 已被顺延三次**，而 MCP 恰是通往 coding agent 最直接的一块积木。

**建议（二选一）**
- 把 M8/M9 明确标注"兴趣支线，可跳"
- 或直接把 MCP 提到 M8 位置，知识图谱与论文推送后置

别让"顺延三次"变成"永远顺延"。

---

### 节奏问题 5：文档在腐化，而腐化的正是入口那篇

| 问题 | 实际情况 |
|---|---|
| `PROJECT_STORY.md` 停在 M5.5（v1.0，写着"接下来 M6"） | `architecture.md` 已到 M6.3 —— 学习者最先读的那篇是过期的 |
| PROJECT_STORY 写"约 700 行" | 实际 **1244 行** |
| 引以为傲的"主循环 121→87 行" | 现 `agent_loop.py` **120 行**（M6 又涨回去），结论在仓库里已看不到 |
| 决策记录是 25 项平铺 bullet list | 单条超 600 字，到 M9 会彻底不可读 |

**建议**
- 决策记录拆成 `docs/adr/NNN-*.md`（一条一文件，正好教 ADR 这个工程实践）
- `architecture.md` 只留架构图 + 现状表 + 索引
- 立规矩：**每个里程碑收尾必须同步 PROJECT_STORY**，否则"给未来的自己"这个定位就废了

## 五、如果只改三件事

| 优先级 | 动作 | 成本 | 解决 |
|---|---|---|---|
| 1 | `main()` 加 `try/finally` 保存 + `session.json` 存 `summary`/`summarized_upto` | 半小时 | 丢历史 + 重启重摘要 |
| 2 | 插入"第一批单测"节点，从 `window_start`/`build_payload` 的覆盖不变量开始 | 一次课 | 贯穿性缺口 |
| 3 | 冻结 evals 语料到 `evals/fixtures/`，`CASES` 移出代码 | 一小时 | 指标可复现性 |

**节奏调整一句话**：M6 收窄到三节，M8/M9 让位给 MCP，M4 收尾补最小容错。
